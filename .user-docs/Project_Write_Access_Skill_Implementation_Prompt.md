# `project-write-access` 구현 작업 프롬프트

아래 프롬프트는 다른 Codex 또는 Claude 세션에서 선택형 권한 관리 스킬을 설계하고 구현할 때 사용한다. 현재 문서에 적힌 가정을 그대로 코드로 옮겨서는 안 된다. 먼저 GitHub·GitLab·Gitea와 각 AI 실행 환경에서 실제로 강제할 수 있는 범위를 검증한 뒤 구현하도록 구성했다.

```text
C:\Agent_Tools_Workspace\harness-kit 저장소에서 사용자용 `project-write-access` 스킬을 설계하고 구현해라.

이 스킬을 만드는 이유는 `.docs` 문서의 소유권을 설명에만 머물게 하지 않기 위해서다. 프로젝트별 Git 계정과 문서 경로를 연결해 권한 밖의 쓰기를 세 지점에서 줄인다. 대상 계층은 ① GitHub·GitLab·Gitea 원격 저장소, ② 개발자 PC의 표준 Git 훅, ③ Codex·Claude의 지침과 쓰기 훅이다. 읽기는 모두 허용하고 쓰기 권한만 `admin > pm-pl > developer`로 상속한다. 이 스킬은 기존 문서 생성 흐름과 독립된 선택 기능이어야 한다. 반드시 사용자가 명시적으로 호출했을 때만 실행돼야 한다.

보호 대상은 `.docs/**`와 같은 저장소에서 함께 관리되는 루트 `AGENTS.md`·`CLAUDE.md`다. 애플리케이션 소스코드의 권한은 기존 저장소 정책에 맡기고 이 스킬이 새로 제한하지 않는다. 다만 AI가 문서 작업과 함께 Git 명령을 실행할 때는 보호 문서가 그 명령에 포함됐는지 검사한다.

가장 먼저 저장소의 `AGENTS.md`를 읽고 지시를 따라라. 그다음 관리자 스킬 `custom-skill-design`을 명시적으로 사용해 스킬 경계·위협 모델·승인 지점·실패 복구 방식을 설계한다. `.user-docs/Multi_App_Doc_Flow_And_Ownership.md`의 9~14절과 단일·복수 레포 예시는 구현 기준으로 읽어라. 특히 14절은 아직 구현되지 않은 스킬을 가정해 쓴 문서다. 문서와 실제 플랫폼 기능이 충돌하면 조용히 맞추지 말고 차이를 먼저 보고한 뒤 검증된 동작을 기준으로 문서도 함께 고쳐라.

코드를 쓰기 전에 다음을 검증해라.

1. GitHub·GitLab·Gitea의 공식 최신 문서로 CODEOWNERS 탐색 위치와 우선순위, 소유자 승인, 보호 브랜치, 직접 push 제한, PR·MR 병합 제한과 관리자 API 범위를 확인한다. 더 높은 우선순위의 기존 CODEOWNERS 때문에 스킬이 만든 파일이 무시되는 경우도 검사한다. 서비스·요금제·버전별로 지원하지 않는 기능은 지원한다고 가정하지 않는다.
2. CODEOWNERS가 로컬 add·commit·push를 막는 파일이 아니라 원격 서비스가 읽는 검토자 지정 파일임을 전제로 한다. 서버 규칙과 결합하지 않았을 때의 한계를 테스트와 문서에 남긴다.
3. 표준 Git에는 `pre-add`가 없고 `pre-commit`·`pre-push`는 `--no-verify` 등으로 우회할 수 있음을 전제로 한다. 로컬 훅을 최종 보안 경계라고 표현하지 않는다.
4. Codex·Claude가 실제로 가로챌 수 있는 파일 편집 도구와 Git 명령 범위를 확인한다. 확인할 수 없는 우회 경로는 차단했다고 주장하지 말고 증적과 제한으로 남긴다.
5. 복수 앱·복수 레포, 단일 앱·단일 레포, 복수 앱·단일 레포를 각각 조사한다. 복수 레포에서는 `.docs`가 별도 저장소이고 컨테이너 루트의 `AGENTS.md`·`CLAUDE.md`가 Git 밖에 있다는 차이를 설계에 반영한다.

검증 결과가 구현 가능한 범위와 맞으면 다음 계약으로 사용자 스킬을 만든다.

- 사용자 스킬 정본은 `skills/project-write-access/`에만 둔다. `.agents/skills/`와 `.claude/skills/`의 관리자용 생성본을 직접 편집하거나 사용자 프로젝트에 스킬을 복사하지 않는다.
- 스킬 머리말(frontmatter)에 `disable-model-invocation: true`를 두어 명시 호출 전용으로 만든다. 일반 파일 편집·커밋·설계 스킬이 이 스킬을 자동 호출하거나 필수 의존성으로 삼지 않게 한다.
- 실행은 읽기 전용 `Plan`과 명시 승인 뒤의 `Apply`를 나눈다. 서버 설정 변경, 로컬 훅 설치·교체, 키 폐기, 관리자 변경은 각각 변경 내용을 보여준다. 승인을 받은 뒤에만 수행한다. 일부 적용이 실패하면 가능한 범위에서 되돌린다. 되돌리지 못한 외부 상태는 정확히 보고한다.
- 최초 설정은 서명된 프로젝트 정책이 없을 때만 허용한다. 이미 원격 저장소가 있으면 호출자의 저장소 관리자·소유자 권한을 확인한 뒤 최초 관리자로 등록한다. 로컬 `git init`만 된 새 프로젝트는 첫 호출자를 관리자로 등록하되 원격 연결 후 재검증 상태를 남긴다.
- 원격 `.docs` 저장소가 있으면 최초 설정과 정책 변경 전에 원격 이력과 최신 정책을 확인한다. 작업 폴더가 깨끗하고 fast-forward가 가능할 때만 동기화한다. 로컬 변경을 지우는 강제 reset은 금지하고, 이력이 갈라졌거나 커밋하지 않은 변경이 있으면 관리자에게 정리를 요청한 뒤 중단한다.
- 프로젝트 식별자와 관리자 서명키를 만든다. 동일한 개인키는 Codex와 Claude의 사용자별 전역 보관 위치에 각각 저장한다. 예시는 `~/.codex/harness-kit/admin-keys/{project-id}.key`, `~/.claude/harness-kit/admin-keys/{project-id}.key`다. 실제 경로가 각 플랫폼에서 업데이트의 영향을 받지 않는 안정된 위치인지 확인한다. 플러그인 캐시·프로젝트 저장소·로그에는 개인키나 인증 토큰을 남기지 않는다. 파일 접근 권한, 중간 상태가 남지 않는 안전한 저장, 실패했을 때의 정리까지 검증한다.
- 공유 정책은 `.docs/harness/access-control/`에 둔다. 최소한 프로젝트 신뢰 정보, 역할 상속, 경로별 최소 쓰기 권한, Git 서비스별 계정 연결, 정책 서명, 생성 파일 목록과 해시를 관리한다. 파일 형식과 서명 방식은 먼저 검증하고 테스트로 고정한다.
- 이후 호출에서는 로컬 관리자 키의 지문과 공유 정책의 서명을 확인한다. 검증된 관리자만 프로젝트와 Git 서비스별 계정을 `admin`, `pm-pl`, `developer`에 연결하거나 정책을 바꿀 수 있게 한다. 키 파일이 로컬에 없어도 일치하는 백업 키를 명시적으로 제시하면 검증할 수 있게 한다.
- 관리자 초기화는 정책 파일 삭제만으로 허용하지 않는다. 기존 또는 백업 관리자 키로 폐기 절차를 승인하고 Codex·Claude의 로컬 키 사본을 정리한 뒤 새 신뢰 정보를 만든다. Git 이력에서 삭제·재생성을 추적할 수 있게 한다. 서명이나 생성 목록이 맞지 않으면 아무것도 바꾸지 않고 중단한다.
- 하나의 정책에서 `.github/CODEOWNERS`, `.gitlab/CODEOWNERS`, `.gitea/CODEOWNERS`를 모두 생성한다. 기존 파일의 사용자 작성 영역은 보존한다. 여러 번 실행해도 결과가 달라지지 않도록 스킬 관리 영역만 갱신한다. 현재 원격 서비스가 해당 파일과 서버 설정을 실제로 읽는지도 확인한다.
- 원격 Git 서비스 설정을 조회하거나 적용하려면 저장소 관리자 권한과 API 인증이 필요함을 사전에 보여준다. 인증 정보는 저장하지 않는다. 권한이 부족하면 CODEOWNERS와 적용 계획만 만들고 서버 계층은 `미적용`으로 보고한다. 프로젝트가 정한 브랜치 정책이 없으면 `dev`·`main` 규칙을 임의로 만들지 않는다.
- 로컬 계층은 서비스별 설정 파일이 아니라 표준 Git 훅으로 만든다. 기존 훅과 `core.hooksPath`를 덮어쓰지 말고 공존·연결·복구 방식을 설계한다. `pre-commit`은 스테이징된 경로, `pre-push`는 보낼 커밋을 검사한다. `git add` 자체를 막았다고 표현하지 않는다.
- AI 계층은 앱별 `agent-instruction.md`와 관련 `*-instruction.md`의 전용 관리 블록, 그리고 지원되는 Codex·Claude 쓰기 훅에 같은 정책을 연결한다. 관리 블록은 `harness-kit:write-access:start`와 `harness-kit:write-access:end` 표시 사이로 한정하고 PL이 작성한 나머지 본문은 보존한다. 현재 프로젝트·Git 계정·대상 앱·경로를 확인할 수 없으면 편집·파일 생성·AI가 실행하는 add·commit·push·PR/MR 명령을 중단하고 소유자에게 제안하도록 한다.
- 로컬 `user.name`과 `user.email`만으로 관리자를 인증하지 않는다. 확인된 Git 서비스 계정과 서명된 계정 연결을 우선하고, 원격 신원을 확인할 수 없으면 보호 문서 변경을 허용하지 않는다.
- 기본 권한은 읽기 허용이다. `admin`은 모든 문서 쓰기 범위를, `pm-pl`은 개발자 범위와 앱별 설계·컨텍스트·지침을, `developer`는 자신의 `.docs/{앱}/impl-doc/{사용자}/**`와 승인된 `.docs` 프로토타입 경로를 쓸 수 있게 한다. 역할과 경로는 코드에 고정하지 말고 서명된 프로젝트 정책에서 읽는다.
- 세 계층의 생성물이 같은 정책 해시를 가리키는지 확인하는 불일치 검사와 미리보기·적용·재검증·제거·관리자 교체·키 분실·서명 변조·부분 실패 테스트를 만든다.

구현이 끝나면 사람이 읽는 문서를 전부 다시 확인해 실제 동작과 다른 설명을 찾아 고쳐라. 최소 범위는 루트 `README.md`, `.user-docs/*.md`, `maintainer/plugin/`의 사람용 Markdown, 설치 안내, 스킬 목록과 릴리스 문서다. 새 스킬의 이름·호출 방식·선택 기능이라는 점·세 계층의 한계·생성 경로·관리자 키 복구 절차·지원하지 않는 기능이 문서마다 다르게 적혀 있지 않은지 추적한다. `.user-docs/Multi_App_Doc_Flow_And_Ownership.md`의 14절은 가정형 표현을 실제 구현에 맞게 바꾼다. 이 프롬프트도 최종 계약과 어긋나면 함께 갱신한다. 문서 링크와 예시도 검사한다.

사용자 스킬 추가는 이 저장소의 `0.x` 버전 정책상 부 버전(MINOR) 승격 대상이다. 현재 버전을 먼저 확인하고 다음 부 버전으로 올려라. `maintainer/plugin/CAPABILITIES.json`, 필요한 관리 목록·평가 범위·manifest·marketplace·변경 이력·릴리스 증적을 함께 갱신한다. 그다음 `harness-plugin-maintainer`를 명시적으로 사용해 플러그인 배포 묶음을 다시 만들고 다음 검증을 실제 저장소의 최신 절차에 맞춰 수행한다.

- 새 스킬 단위 평가와 실패 주입 테스트
- 전체 사용자 스킬 평가
- 같은 입력에서 같은 결과가 나오는 플러그인 빌드와 `--check`
- 플러그인 구조·manifest·라이선스 검증
- Codex·Claude CLI 격리 설치 확인(smoke)
- 설치 표면 확인
- 관리자용 생성본 검사
- 릴리스 회귀 검사
- 사람용 문서의 링크·버전·스킬 수·예시 불일치 검사

검증이 모두 통과하면 변경 범위를 다시 확인한다. Conventional Commits 형식의 한글 커밋 메시지로 커밋한 뒤 현재 작업 브랜치를 원격에 push해라. 푸시된 marketplace와 양 플랫폼 manifest가 새 버전을 가리켜 설치 사용자가 플러그인 업데이트로 받을 수 있는 상태인지 확인한다. tag·GitHub Release·released lock 갱신은 저장소의 릴리스 게이트와 별도 승인 규칙을 따른다. 게이트가 충족되지 않았으면 release-ready로 표시하거나 우회하지 마라. 커밋·푸시된 후보 버전과 남은 수동 증적을 보고해라.

최종 보고에는 다음을 포함해라.

1. 검증 뒤 확정한 실제 강제 범위와 남은 우회 가능성
2. 최초 설정·이후 계정 관리·관리자 교체 흐름
3. 세 계층에서 생성·수정한 파일과 외부 설정
4. 사람용 문서에서 찾아 고친 괴리
5. 실행한 평가·빌드·설치·회귀 검증 결과
6. 승격한 버전, 커밋, push 결과와 플러그인 업데이트 가능 여부
7. 게시하지 못했다면 막힌 릴리스 게이트와 필요한 후속 증적
```
