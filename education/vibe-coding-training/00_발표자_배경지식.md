## 1. superpowers — 대표 스킬 요약

> **한 문장 정의**: `superpowers`는 **Claude Code용 검증된 스킬 팩**(Plugin) — 커뮤니티에서 자주 쓰이는 워크플로우를 스킬로 묶어 배포한 묶음.
> **선정 이유(왜 이걸 예로 드나)**: GitHub ★ **약 252k** (2026-07-11 확인 · 저자 Jesse Vincent/obra) — Claude Code 계열 스킬 팩 중 **가장 많이 참조·이용되는 저장소**. 개발자 플랫폼(GitHub)에서 별 수·이용 지표로 검증된 사실상 커뮤니티 표준.
> **설치**: `/plugin marketplace add obra/superpowers-marketplace` → `/plugin install superpowers` (설치 후 각 스킬은 자동 트리거 or `/스킬명`으로 명시 호출).

### 1-1. 데모에서 실제 쓰는 스킬

| 스킬 | 트리거 | 하는 일 | 데모 안에서 등장 시점 |
|------|--------|---------|------------------------|
| **`brainstorming`** | `/brainstorming` 또는 "설계·기획" 관련 요청 | 즉시 구현하지 않고 요구를 캐물어 **설계 `.md`** 를 먼저 뽑는다. AI가 사용자에게 되묻는 절차 자체가 스킬. | D4 대본 단계 ① |
| **`commit`** | 커밋 상황 자동 | 변경 분석 → Conventional Commits 규칙의 메시지 자동 생성 후 커밋. | (라이브 시연 안 하지만 언급) |

### 1-2. 언급만 하고 넘어갈 스킬 (질문 시 답용)

| 스킬 | 하는 일 |
|------|---------|
| `verify` | 변경이 실제로 동작하는지 end-to-end로 굴려 확인 |
| `code-review` | 변경 diff 리뷰 (correctness·simplification·efficiency) |
| `simplify` | 리뷰 결과 직접 반영 (품질 정리 전용) |
| `run` | 프로젝트를 실행해 결과 눈으로 확인 |
| `init` | 저장소에 최초 `CLAUDE.md` 생성 |
| `security-review` | 변경분에 대한 보안 관점 리뷰 |

### 1-3. superpowers의 위상 (개념 정리)

- **Plugin** = 스킬 여러 개 + 설정 + 훅을 한 팩으로 배포하는 단위
- superpowers는 **가장 유명한 오픈 Plugin** 중 하나
- 개인이 만든 스킬도 같은 `SKILL.md` 규격이면 어디서든 동일 방식으로 붙는다 → ②덱 클라이맥스("표준으로 수렴")의 실사례

### 1-4. 심화 예시 — `gstack` (Plugin이 아닌 방식)

> **한 문장 정의**: **`garrytan/gstack`**은 Claude/Codex를 **가상 제품 개발 팀**처럼 운영하도록 한 하네스 — CEO·design·eng review·QA·ship·CSO 같은 **역할별 slash command**로 개발 단계를 나눈다.
> **선정 이유**: GitHub ★ **약 121k** (2026-07-11 확인 · 저자 Garry Tan, Y Combinator 대표) — 하네스가 어디까지 세밀해질 수 있는지 보여주는 대표 사례.

**superpowers와 다른 점 (라이브에서 대비 포인트)**:

| 축 | `superpowers` | `gstack` |
|----|---------------|----------|
| 성격 | 방법론형 (brainstorm→plan→TDD→review→finish) | 역할형 (팀처럼 운영) |
| 대표 명령 | `/brainstorming`, `/commit`, `/verify` | `/office-hours`, `/review`, `/qa`, `/ship` |
| **배포 방식** | **Plugin marketplace** (`/plugin install`) | **Plugin 없음 · 직접 `git clone`** 후 특정 위치에 배치 |
| 설치 대상 위치 | Claude Code가 자동 관리 | 사용자가 명시적으로 `~/.claude/skills/gstack` 등에 두고 `./setup` 실행 |

**gstack 설치 예 (라이브에서 Q&A 나오면 그대로 보여줄 수 있음)**:

```bash
# 사용자 전역 (Claude Code)
git clone --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack && ./setup

# Codex CLI 전역
git clone --depth 1 https://github.com/garrytan/gstack.git ~/.codex/skills/gstack
cd ~/.codex/skills/gstack && ./setup --host codex

# 프로젝트 전용
cd $REPO_ROOT
git clone --depth 1 https://github.com/garrytan/gstack.git .claude/skills/gstack
cd .claude/skills/gstack && ./setup
```

> **회수 포인트**: "**스킬은 다양하고, 배포 방식도 다양하다.** 그런데 공통은 언제나 `.md` 규격 하나다." — §1 관통 주장의 보강.

### 1-5. 스킬 생태계 다양성 (Q&A 대비 참고 카드)

Claude Code/Codex 커뮤니티에서 자주 언급되는 하네스형 저장소 3개 (2026-07-11 확인):

| 저장소 | ★ | 성격 | 접근 방식 |
|--------|:---:|------|-----------|
| `obra/superpowers` | ~252k | 개발 방법론 강제 | Plugin |
| `garrytan/gstack` | ~121k | 역할 기반 가상 팀 | 직접 clone + `./setup` |
| `multica-ai/andrej-karpathy-skills` | ~191k | Karpathy 4원칙 행동 규범 | Plugin 또는 `CLAUDE.md` 삽입 |

> ⚠️ **stars는 변동성이 큽니다.** 발표 당일 다시 확인 권장. 위 수치는 참고용.

**정리 메시지**: "어떤 건 Plugin으로, 어떤 건 clone으로. 방식이 다양해도 **결국 `SKILL.md` 하나로 붙는다**."

## 2. 용어 풀이 (1줄 사전 · 참석자 눈높이)

### 2-1. 오늘의 핵심 5개 (반드시 유창하게)

| 용어 | 한 줄 풀이 | 오해 방지 노트 |
|------|------------|-----------------|
| **바이브코딩** | 자연어 의도만 말해도 AI가 코드를 만들어주는 개발 방식 | "자동 코딩"이 아님 — **의도 전달의 정확성**이 관건 |
| **프롬프트 엔지니어링** | 같은 요청도 어떻게 '말'하냐로 결과가 갈리기에, 지시를 설계하는 기술 | 요령·팁 모음이 아님 — 4요소(참조·범위·금지·완료기준) 체계 |
| **하네스(harness) 엔지니어링** | 말이 아니라 **문서로 구조**를 깔아, AI가 팀 기준으로 일하게 잡아주는 것 | 하네스 = 마구·안전벨트. "제약이 아니라 방향" |
| **`.md`(마크다운 문서)** | AI가 규칙·스킬·컨텍스트를 인식하는 **공통 규격 파일** | 왜 하필 md? — 사람도 AI도 잘 읽는 최소 공통분모 |
| **superpowers** | Claude Code용 **검증된 스킬 팩(Plugin)** — 오늘 시연의 도구 | 반드시 필요한 게 아님. 없어도 하네스는 성립 |

### 2-2. `.md` 3종 (②덱 클라이맥스·③덱 클라이맥스 회수 대상)

| 파일 | 사는 곳 | 역할 |
|------|---------|------|
| **`SKILL.md`** | `skills/{스킬명}/SKILL.md` | 스킬 하나의 정의 — 언제 트리거, 무엇을 하는지, 예시 |
| **`CLAUDE.md`** | 프로젝트 루트 (또는 `.claude/`) | Claude가 이 프로젝트에서 지켜야 할 규칙·컨텍스트 |
| **`AGENTS.md`** | 프로젝트 루트 (또는 `.agents/`) | Codex·Antigravity 등 **여러 에이전트 공용** 규칙 |

> **정답 프레이밍**: "이 세 파일 이름만 기억해도 오늘 절반은 남는다."

### 2-3. 도구·확장 개념

| 용어 | 한 줄 풀이 |
|------|------------|
| **Skill** | 재사용 가능한 전문 능력 팩. `SKILL.md` + 스크립트/템플릿 구성. 의미 기반 자동 트리거. |
| **Plugin** | 스킬·서브에이전트·훅 여러 개를 묶어 배포하는 팩 (예: superpowers). 2025-10 Anthropic 공식 지원. |
| **MCP (Model Context Protocol)** | 외부 도구(Notion, GitHub, DB 등)를 AI가 참조하게 하는 **개방 프로토콜**. Anthropic이 **2024-11-25** 오픈소스로 공개. |
| **Command / Workflow** | 슬래시로 명시 호출(`/명령어`). Antigravity의 `workflows`는 스킬 여러 개를 파이프라인처럼 엮는 상위 개념. |
| **Hook** | 특정 이벤트(도구 호출 전후 등)에 실행되는 스크립트. 자동화 훅. |
| **Memory** | AI가 자동 로드·유지하는 사용자·프로젝트 기억. 3사 다 보유, 위치는 제각각. |
| **Context (컨텍스트)** | 프로젝트에서 AI가 매번 읽는 규칙·상황 문서 (주로 `CLAUDE.md`·`AGENTS.md`). |
| **전역 스코프(사용자 홈 설치)** | 스킬·서브에이전트·Plugin·훅을 사용자 홈(`~/.claude/`, `~/.codex/`, `~/.gemini/config/`)에 두어 **모든 프로젝트에서 공유**. 자주 쓰는 건 여기로. |
| **프로젝트 스코프** | `<프로젝트>/.claude/`, `<프로젝트>/.agents/` 아래 배치. 해당 저장소에서만 유효. 프로젝트 특화 규칙·팀 공유용. |

### 2-3-1. 전역 vs 프로젝트 — 어디에 둘까 (실무 가이드)

| 도구 | 전역 (사용자 홈) | 프로젝트 |
|------|-------------------|----------|
| **Claude** | `~/.claude/skills/`, `~/.claude/agents/`, `~/.claude/plugins/` | `<proj>/.claude/skills/`, `.claude/agents/` |
| **Codex** | `~/.codex/skills/` | `<proj>/.agents/skills/`, `<proj>/.codex/skills/` |
| **Antigravity** | `~/.gemini/config/skills/` | `<proj>/.agents/skills/` |

**판단 기준**:
- **전역**: 여러 프로젝트에서 반복 사용, 개인 습관·관례 (예: `commit`, `brainstorming`, 개인 서브에이전트)
- **프로젝트**: 팀 공유 규칙, 저장소 특유 워크플로우, 사내 스킬 (팀 저장소에 커밋)

> **회수 문장**: "어디에 두든 **규격은 같은 `.md`** — 위치(스코프)만 다르다."

## 3. 자주 나올 Q&A 대비

### 3-1. 개념 관련

**Q. "결국 문서 쓰기"가 프롬프트 엔지니어링과 뭐가 다른가요?**
A. 프롬프트는 **1회성 말버릇**입니다. 다음 사람에게 안 남습니다. 문서(`.md`)는 **팀에 남는 규격**입니다. 오늘 요점은 "매번 잘 말하기"가 아니라 "한 번 잘 써두기"입니다.

**Q. `.md`만 쓴다고 팀에서 다 되나요? 사람마다 스타일이 다를 텐데.**
A. 그래서 규격이 있습니다. `SKILL.md`는 필드가 정해져 있고, `CLAUDE.md`도 프로젝트마다 관례가 자리 잡고 있습니다. 무엇보다 **AI가 이 파일을 자동으로 읽습니다** — 형식을 벗어나면 AI가 알아채 못하니 강제력이 있습니다.

**Q. 초보자도 이걸 할 수 있나요?**
A. 오히려 코드 몰라도 됩니다. 문서를 쓰는 감각만 있으면 됩니다. **오늘 데모의 발표자도 초기 요청은 한 문단짜리 자연어입니다.**

**Q. 개인이 아니라 회사에서 도입하려면?**
A. `CLAUDE.md`·`AGENTS.md`에 팀 규칙을 문서화하고, 자주 하는 절차를 `SKILL.md`로 뽑아 공유 저장소에 두는 것부터. superpowers처럼 팀 전용 Plugin을 만들 수도 있습니다.

### 3-2. 도구·플랫폼 관련

**Q. Claude·Codex·Antigravity 중에 뭐 써야 하나요?**
A. **`.md` 규격이 공통**이라 어느 걸 쓰든 문서 자산은 이동합니다. 도구 선택은 UI 취향·가격·통합 여부로 결정하시면 됩니다. 오늘 데모는 Claude Code를 씁니다.

**Q. superpowers 없으면 못 하나요?**
A. 없어도 됩니다. superpowers는 **"이미 만들어진 좋은 예"** 입니다. 직접 만든 `SKILL.md` 하나로도 하네스는 성립합니다.

**Q. superpowers 말고 다른 하네스는 뭐가 있나요?**
A. `garrytan/gstack`(약 121k stars, Y Combinator 대표 Garry Tan)이 대표적입니다. superpowers가 방법론 강제형이라면 gstack은 **역할 기반** — `/office-hours`, `/review`, `/qa` 같은 명령으로 팀처럼 운영합니다. 다만 **Plugin marketplace로 배포되지 않아서** Claude/Codex 앱에서 클릭 한 번으로 못 받고, 저장소를 직접 `git clone`해서 `~/.claude/skills/gstack` 같은 위치에 두고 `./setup`을 실행해야 합니다. 그 외 `multica-ai/andrej-karpathy-skills`(약 191k stars, Karpathy 4원칙)도 있습니다.

**Q. 스킬·서브에이전트·Plugin을 매 프로젝트마다 새로 설정해야 하나요?**
A. 아니요. **사용자 홈에 두면 전역(모든 프로젝트에서 자동 사용)** 이 됩니다.
- Claude: `~/.claude/skills/`, `~/.claude/agents/`
- Codex: `~/.codex/skills/`
- Antigravity: `~/.gemini/config/skills/`

자주 쓰는 스킬·서브에이전트·Plugin을 여기 한 번만 설치하면 어느 프로젝트에서 열든 즉시 붙습니다. 팀 저장소에서만 통용될 규칙은 프로젝트 스코프(`<proj>/.claude/`, `.agents/`)에 두면 됩니다.

**Q. Antigravity의 `workflows`는 뭐예요?**
A. 여러 스킬을 파이프라인처럼 엮는 상위 개념입니다. 유효하지만 **플랫폼 특수**입니다. 오늘은 **보편 단위인 Skill**을 앞세웠습니다 — 어디서나 통하니까요.

**Q. MCP를 꼭 써야 하나요?**
A. 아뇨. 외부 도구를 연결하고 싶을 때만 씁니다. 오늘의 TODO 앱 데모에는 MCP가 필요 없습니다.

### 3-3. 데모 관련

**Q. Electron 무겁지 않아요? Tauri가 낫지 않나요?**
A. 개인용 규모에선 용량이 문제가 아닙니다. Tauri는 Rust 툴체인 이슈로 라이브 셋업 부담이 있어 오늘은 Electron으로 갔습니다. **설계 `.md`만 있으면 Tauri로 갈아치우기 쉽습니다** — 그것이 오늘 요점입니다.

**Q. 왜 DB 안 써요?**
A. 요구가 개인용 + 사용자가 데이터 위치를 통제. 파일이 답입니다. 규모 커지면 SQLite로 승격 가능한데, 그때도 **설계 `.md`가 근거**가 됩니다.

**Q. 재현 시연이 결국 캐시된 대화 아닌가요?**
A. 브랜치 새로 만들어 코드 삭제 → 새 세션으로 시연하면 캐시가 아닙니다. 오늘 라이브는 시간상 절충한 형태입니다. **핵심은 "문서만 남기고도 같은 결과가 나온다"** 는 원리 자체입니다.

**Q. 이거 나도 오늘 집에 가서 시작할 수 있나요?**
A. Node.js + Claude Code 설치 → superpowers 설치 → `/brainstorming` 한 번이면 시작입니다. 이 대본(`D4_라이브데모_대본.md`)도 자기 팀에서 재현할 수 있게 나눠드릴 수 있습니다.

**Q. `.exe` 파일 만들면 다른 사람 컴퓨터에서도 그냥 실행되나요?**
A. Windows용은 됩니다(코드 서명 별개). Mac·Linux는 각각 별도 빌드가 필요합니다. `electron-builder`가 지원합니다.

### 3-4. 회의적·비판적 질문

**Q. AI가 뻘짓하면 문서가 있어도 소용없지 않아요?**
A. 있어야 되돌리기가 됩니다. 문서가 없으면 "저번엔 잘 됐는데" 라는 말만 남습니다. 문서가 있으면 **다시 가리키기**로 궤도 수정이 가능합니다. 오늘 라이브에서 실제로 이 순간이 나올 겁니다.

**Q. 매번 이렇게 문서부터 쓰면 오히려 느려지지 않나요?**
A. 첫 회는 살짝 느립니다. 두 번째부터 훨씬 빨라집니다. 그리고 **다음 사람이 붙는 순간의 속도**가 압도적으로 다릅니다.

**Q. 이 방식이 정말 정착될까요? 유행 아닌가요?**
A. ②덱 마지막 슬라이드가 그 답이었습니다 — **세 대형 랩이 같은 `.md` 규격으로 조용히 수렴**했습니다. 유행이 아니라 표준입니다.

## 5. 관통 주장(§1) 회수 스크립트 (라이브에서 잊으면 여기 조회)

**오늘의 한 문장**:
> **코드를 짜는 능력이 아니라, 문서(프롬프트)를 쓰는 능력이 AI 시대의 핵심 역량이다.**

**5개 회수 포인트 (D4 대본에서 발췌)**:

1. **[설계 `.md` 완성 직후]** "지금까지 AI가 만든 건 코드가 아니라 **문서**입니다."
2. **[구현 요청 직후]** "제가 다시 설명한 게 아니라 **문서를 가리켰을 뿐**입니다."
3. **[`todos.json` 공개]** "**DB 없어요. 파일 하나입니다.**"
4. **[주간보고 `.md` 공개 — 주 회수]** "코드는요? 코드는 이 두 문서 사이에 잠깐 있었을 뿐입니다."
5. **[재현 성공 — 최종 회수]** "코드는 사라져도, **문서만 있으면 돌아옵니다.**"

**마무리 문장 (Q&A 진입 직전)**:
> "오늘 만든 `.exe`는 나중에 잃어버려도 괜찮습니다. 여러분 손에는 `design/todo-app.md`가 있으니까요.
> 그리고 그 문서를 쓰는 감각 — 오늘 여러분이 가져가시는 건 그거 하나입니다."
