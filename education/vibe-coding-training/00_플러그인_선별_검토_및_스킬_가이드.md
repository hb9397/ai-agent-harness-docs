# Superpowers · Product Design 플러그인 스킬

## 핸드오프

이 플러그인 하네스를 적용하기 전에 대상 프로젝트의 context 문서를 먼저 작성해야 한다. 플러그인 스킬은 사용자의 요청을 처리하는 실행 도구이고, context 문서는 프로젝트의 목적, 화면 기준, 기술 제약, 산출물 규칙을 고정하는 기준 문서다.

적용 순서는 다음과 같다.

| 순서 | 작업 | 목적 |
| --- | --- | --- |
| 1 | context 문서 작성 | 프로젝트 목적, 대상 사용자, 주요 화면, 디자인 기준, 기술 제약, 검증 기준을 정리한다. |
| 2 | `.docs/.instruction` 구성 | 반복 적용할 작업 규칙, 문서 규칙, 디자인 규칙, 검증 규칙을 파일로 분리해 둔다. |
| 3 | `AGENTS.md`, `CLAUDE.md` 작성 또는 갱신 | 에이전트가 `.docs/.instruction`의 규칙을 먼저 참고하도록 지시한다. |
| 4 | 플러그인 하네스 적용 | Superpowers와 Product Design 스킬을 context와 instruction 기준에 맞춰 사용한다. |
| 5 | 규칙 갱신 | 교육 중 발견한 기준 변경 사항을 `.docs/.instruction`에 반영하고, `AGENTS.md`, `CLAUDE.md`가 계속 그 경로를 참조하도록 유지한다. |

`AGENTS.md`와 `CLAUDE.md`는 규칙을 길게 인라인으로 반복하기보다 `.docs/.instruction`을 참고하는 형태로 작성한다. 이렇게 해야 프로젝트 규칙이 바뀔 때 instruction 문서만 갱신해도 여러 에이전트가 같은 기준을 따를 수 있다.

예시 구조:

```text
.docs/
  context/
    project-context.md
  .instruction/
    agent-rules.md
    design-rules.md
    verification-rules.md
    output-rules.md
AGENTS.md
CLAUDE.md
```

`AGENTS.md`, `CLAUDE.md`에는 다음 성격의 내용을 둔다.

```text
작업 전에 .docs/context/project-context.md를 읽는다.
작업 규칙은 .docs/.instruction/ 하위 문서를 따른다.
규칙이 변경되면 .docs/.instruction/ 문서를 갱신하고, AGENTS.md와 CLAUDE.md의 참조가 유지되는지 확인한다.
```

## 사용할 스킬 목록

하네스 구성에는 전체 스킬을 모두 넣지 않는다. 기본 흐름은 `Superpowers`로 작업 순서와 검증을 잡고, `Product Design`으로 화면 방향·프로토타입·디자인 QA를 처리한다.

### 기본 사용 스킬

| 플러그인 | 스킬명 | 사용 시점 | 역할 |
| --- | --- | --- | --- |
| Superpowers | `brainstorming` | 작업 기준 정리 시 | 아이디어를 작업 가능한 요구사항으로 구체화 |
| Product Design | `ideate` | 시각 방향이 필요할 때 | 선택 가능한 디자인 방향을 이미지 기반으로 생성 |
| Superpowers | `writing-plans` | 구현 전에 | 구현 단계를 작게 쪼개 계획으로 정리 |
| Superpowers | `executing-plans` | 구현 계획 작성 후 | 구현 계획 문서의 각 단계를 순서대로 수행 |
| Product Design | `image-to-code` | 선택한 시각안이 있을 때 | 이미지·스크린샷·목업을 참고해 프론트엔드 화면 구성과 디자인을 구현 |
| Product Design | `url-to-code` | 기존 URL을 재현할 때 | 라이브 화면을 참고해 프론트엔드 화면 구성과 디자인을 구현 |
| Product Design | `design-qa` | 전달 전 | 원본 시각 자료와 구현 결과를 비교해 수정 목록을 도출 |
| Superpowers | `verification-before-completion` | 완료 보고 전 | 실제 검증 결과를 확인한 뒤 완료 여부를 판단 |

### 스킬을 포함한 프롬프트 작성예시

스킬명만 말하는 대신, 무엇을 기준으로 어떤 산출물을 만들어야 하는지 프롬프트에 명시한다. 특히 문서 산출물은 저장 경로와 파일명 규칙을 함께 지정한다.

| 단계 | 스킬명 | 프롬프트 예시 |
| --- | --- | --- |
| 1 | `brainstorming` | “`OOO 기능` 아이디어를 실제 화면으로 만들 수 있게 요구사항을 구체화하고, 그 내용을 `.docs/impl_plans/` 디렉토리에 `yyyy-mm-dd_OOO기능_brainstorming.md` 파일로 작성해줘. 목적, 사용자 흐름, 필수 상태, 성공 기준, 제외 범위, 선택 가능한 접근안 2~3개를 포함해줘.” |
| 2 | `writing-plans` | “`@.docs/impl_plans/yyyy-mm-dd_OOO기능_brainstorming.md` 내용을 참고해서 `OOO 기능` 구현 계획을 `.docs/impl_plans/` 디렉토리에 `yyyy-mm-dd_OOO기능_impl_plan.md` 파일로 작성해줘. 화면 구조, 컴포넌트, 상태, 상호작용, 검증 방법, 산출물 위치를 단계별 체크리스트로 쓰고, 구현 완료 후 `design-qa`, `verification-before-completion`, `requesting-code-review`를 요청해야 하는 시점까지 포함해줘.” |
| 3 | `executing-plans` | “`@.docs/impl_plans/yyyy-mm-dd_OOO기능_impl_plan.md` 문서를 읽고 각 단계를 순서대로 수행해줘. 프론트엔드 화면 작업 단계에서는 필요한 경우 `ideate`로 시각 방향을 먼저 정하고, 선택한 자료에 따라 `image-to-code` 또는 `url-to-code`를 고려해서 구현해줘. 각 단계마다 완료 조건과 검증 결과를 확인하고, 막히면 추측하지 말고 질문해줘.” |
| 조건부 | `ideate` | “확정된 작업 기준과 `.docs/.instruction/design-rules.md`를 기준으로 `OOO 기능` 화면의 시각 디자인 방향을 3개 제안해줘. 각 방향은 레이아웃, 톤, 주요 컴포넌트 차이가 드러나게 만들어줘.” |
| 조건부 | `image-to-code` | “선택한 시각안 또는 `@목업파일`을 참고해서 `OOO 기능`의 프론트엔드 화면 구성과 디자인을 구현해줘. `.docs/.instruction/design-rules.md`와 `.docs/.instruction/output-rules.md`를 지키고, 실행 가능한 프로토타입과 로컬 실행 방법을 함께 남겨줘.” |
| 조건부 | `url-to-code` | “`https://example.com/OOO` 화면을 참고해서 `OOO 기능`의 프론트엔드 화면 구성과 디자인을 만들어줘. 원본의 화면 구조, 주요 상호작용, 시각 스타일을 참고하되 실제 서비스 데이터나 백엔드는 복제하지 말고, 참고·학습용 로컬 프로토타입으로 작성해줘.” |
| 조건부 | `design-qa` | “구현된 `OOO 기능` 프로토타입을 원본 목업 또는 선택한 시각안과 비교해줘. 레이아웃, 타이포그래피, 색상, 이미지 품질, 문구, 반응형 상태를 점검하고 `design-qa.md`에 P0/P1/P2/P3로 정리해줘.” |
| 4 | `verification-before-completion` | “완료라고 말하기 전에 로컬 실행, 빌드 결과, 디자인 QA 결과를 확인해줘. 확인한 명령과 결과를 근거로 완료 여부와 남은 이슈를 정리해줘.” |
| 조건부 | `share` | “이미 만들어진 `OOO 기능` 프로토타입을 공유 가능한 미리보기 URL로 게시해줘. 운영 배포가 아니라 리뷰와 피드백용 링크임을 명시하고, 배포 대상과 접근 URL을 알려줘.” |
| 조건부 | 스킬 없이 Docker/Podman | “`OOO 기능` 프로토타입을 `share` 스킬 없이 Docker 또는 Podman 컨테이너로 실행 가능한 상태로 만들어줘. `Dockerfile`, 실행 명령, 포트 매핑, 중지 명령을 문서화하고 로컬에서 접속 가능한 URL을 알려줘.” |

### 요청 유형별 최소 조합

새 화면 또는 기능 아이디어를 프로토타입으로 만들기:

```text
[자동] Superpowers / using-superpowers - 작업 시작 시 자동 호출되어 이번 요청에 필요한 스킬을 선별한다.
↓
1. Superpowers / brainstorming - 목적, 제약, 참고할 시각 기준, 상호작용 수준, 성공 기준을 작업 가능한 요구사항으로 구체화한다.
↓
2. Product Design / ideate - 확인된 디자인 기준을 바탕으로 선택 가능한 시각 디자인 방향을 만든다.
↓
3. Superpowers / writing-plans - 화면, 상태, 상호작용, 검증 단계를 실행 가능한 작업 순서로 나눈다.
↓
4. Superpowers / executing-plans - 구현 계획 문서의 각 단계를 순서대로 수행하며, 프론트엔드 작업에서는 ideate, image-to-code, url-to-code 적용 여부를 판단한다.
↓
5. Product Design / image-to-code - 선택된 시각안을 참고해 프론트엔드 화면 구성과 디자인을 구현한다.
```
