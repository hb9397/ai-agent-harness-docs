## 1. 관통 주장 (Thesis) — 이 교육이 남길 단 하나

> **코드를 짜는 능력이 아니라, "문서(프롬프트)를 쓰는 능력"이 AI 시대의 핵심 역량이다.**

여기서 "문서를 쓰는 능력"은 두 가지를 뜻한다.

1. **맥락 공급** — 내 의도·사전지식·규칙을 AI가 알아듣게 문서로 정확히 전달하는 능력
2. **질의 능력** — 내가 모르는 것을 AI에게 캐물어 끌어내고, 그 결과를 다시 문서로 정리하는 능력

교육 전체는 **여러 개념을 나열하지 않는다.** 바이브코딩·프롬프트 엔지니어링·하네스 엔지니어링 세 개념은 전부 이 한 문장으로 수렴하기 위한 사다리일 뿐이다. 그리고 그 "문서"의 실제 형태가 곧 **`.md`**(CLAUDE.md / AGENTS.md / instruction / skills)다.

### 보조 주장 — "표준화로의 수렴"

> 개별 플랫폼의 특수 개념은 **생겼다 사라지고**, 결국 대표 플랫폼들이 서로에게 맞추며 **보편 표준으로 수렴**한다. 그러니 플랫폼별 디테일보다 **지금 보편적으로 통용되는 `.md` 구조 패턴**을 익히는 것이 남는 역량이다.

- **근거(검증됨)**: Skills가 **오픈 표준**으로 수렴 중 — Anthropic이 2025-12-18 Agent Skills 표준 공개 → 48시간 내 MS·OpenAI 지원 → 2026-01 Google Antigravity 채택 → 2026-03 32개 도구 돌파(동일 `SKILL.md`·폴더 구조). "표준위원회도 공동발표도 없이 조용히 수렴".
- **함의(교육 태도)**: **Antigravity `workflows` 같은 플랫폼 특수 개념은 강조하지 않는다.** (여전히 유효하지만 보편 단위가 아니라 그 플랫폼의 오케스트레이션 계층 — 여러 skill을 엮는 파이프라인.) 대신 **어디서나 통하는 skill·context 문서(`CLAUDE.md`/`AGENTS.md`)·`.md` 문서 구조 패턴**을 핵심으로 둔다.

### Spine (개념 → 실적용을 잇는 한 줄)

> "AI에게 코드를 시키는 것"에서 → "AI가 같은 기준으로 일하도록 **문서로 구조를 깔아두는 것**"으로.

## 2. 대상 · 목표

### 2-1. 대상
- 코드 작성 경험이 전제되지 않는 참석자.
- **자료·발표 중 이 사실을 명시적으로 언급하지 않는다.** 대신 진입 장벽만 낮춘다: 자연어 중심 설명, 환경 설정은 시연으로 대체, 용어는 첫 등장 시 1줄 풀이.

### 2-2. 학습 목표 (교육이 끝나면)
1. 바이브코딩 / 프롬프트 / 하네스가 **왜 결국 "문서 쓰기"로 모이는지** 한 문장으로 말할 수 있다.
2. `CLAUDE.md` · `AGENTS.md` · `skills`가 **플랫폼 공통 `.md` 규격**임을 알고, "한 번 익히면 어디서나 통한다"를 이해한다.
3. 실제 바이브코딩(superpowers)이 **어떻게 문서 중심으로 굴러가는지** 데모로 목격한다.

## 3. 전체 구성 — PPT 3개 분리

| 덱 | 이름 | 역할 | 주장과의 관계 | 형태 |
|----|------|------|----------------|------|
| **① 개념** | 개념 발전 서사 | 바이브→프롬프트→하네스 등장배경·핵심개념 | **주장을 세운다** ("결국 문서 쓰기") | 신규 제작 |
| **② 구성요소** | 지금 가진 덱 + 보완 | AI Docs/Skills/Commands/Hooks/MCP/Subagent 레퍼런스 | **주장을 실증한다** ("그 문서가 이렇게 생겼다") | 기존 14장 보강 |
| **③ 실적용** | 실제 적용 예시 | superpowers로 라이브 시연 | **주장을 증명한다** (문서 중심으로 실제로 돈다) | 신규 제작 + 데모 대본 |

> **강조 지점**: 관통 주장(§1)은 ①에서 "주장"으로, ②에서 "실증"으로 **두 번 등장**한다. ①은 왜 문서가 핵심인지, ②는 그 문서가 실제로 어떤 `.md`인지. 나열이 아니라 같은 메시지의 반복 회수.

### 3-1. 아젠다 / 시간 배분 (기준 2.5h = 150분, 2~3h 유연) — O1 확정

| 구간 | 내용 | 2h(compact) | **2.5h(기준)** | 3h(확장) |
|------|------|:---:|:---:|:---:|
| 오프닝 | 인사·목표·오늘의 한 문장(§1) | 5 | 5 | 10 |
| ①덱 개념 서사 | 바이브→프롬프트→하네스 → "문서 쓰기" 착지 | 25 | 30 | 35 |
| ②덱 구성요소 | 표면·`/`·`@`·경로 → 부품 도감 → `.md` 클라이맥스 (가볍게) | 25 | 30 | 40 |
| 휴식 | | 5 | 10 | 10 |
| ③덱 실적용 | superpowers 소개·하네스 실증·MCP/Plugin | 20 | 25 | 30 |
| 라이브 데모 | 설계→`.md`→산출물→재현 (버퍼 포함, **flex**) | 20 | 30 | 40 |
| Q&A·마무리 | 주장 회수·질문 | 10 | 20 | 25 |
| **합계** | | **110** | **150** | **190** |

**첫 진행 대비 원칙**
- **데모는 flex 구간** — 라이브는 늘 초과된다. 밀리면 **데모를 줄이고 개념 회수(마무리)를 지킨다**.
- **②덱은 깊이 파지 않는다** — 밀도가 높으니 "이런 게 있다 + 결국 `.md`"로 빠르게 통과.
- 2h면 휴식·Q&A를 줄이고, 3h면 데모·Q&A를 늘린다.
- 개념(①②)≈65분 / 실적용(③+데모)≈55분 → 에너지·기억의 정점은 **데모**에 둔다.

## 4. PPT ① — 개념 발전 서사

### 4-1. 핵심 구조: 3단 상승 사다리
개념을 나열하지 않는다. **한 단계가 다음 단계의 필요성을 낳는 오르막**으로 배치하고, 마지막을 §1 주장으로 착지시킨다.

| 단계 | 개념 | 등장 배경 (왜 나왔나) | 핵심 개념 | 다음 단계로 넘기는 갈고리 |
|------|------|------------------------|-----------|----------------------------|
| 1 | **바이브코딩** | 자연어로 의도만 말해도 AI가 코드를 만든다 | "무엇을 원하는지 전달"이 곧 개발 | "근데 매번 결과가 다르던데?" |
| 2 | **프롬프트 엔지니어링** | 같은 요청도 어떻게 '말'하냐에 따라 결과가 갈린다 | 좋은 지시 4요소(참조·범위·금지·완료기준), 질의로 사전지식 끌어내기 | "말은 휘발된다. 팀·다음 사람에 안 남는다" |
| 3 | **하네스 엔지니어링** | 말버릇을 넘어 **문서로 구조를 고정**해 반복·재현 | 마구/안전벨트 은유, 작업 흐름(설계→컨텍스트→구현→검증) | (→ 착지) "세 개념이 결국 **문서 쓰기** 하나로 모인다" |

### 4-2. 단계별 메시지 뼈대

**단계 1 — 바이브코딩**
- 정의: 자연어 의도 → 산출물.
- 함정 제시: "그냥 시키면" 사람마다·매번 결과가 다르다 → 편차/재작업.
- 전환 질문: "그럼 내가 하는 일은 뭐지?" → **"원하는 걸 정확히 전달하는 일"**.

**단계 2 — 프롬프트 엔지니어링**
- 좋은 지시의 4요소: ①참조할 것 ②이번 범위 ③건드리면 안 되는 것 ④완료 기준.
- Before/After 프롬프트 1쌍.
- **여기서 "질의 능력" 강조**: 모르는 건 AI에게 캐물어 사전지식을 끌어낸 뒤 문서로 정리한다 (§1-2).
- 한계 지적: 프롬프트는 **1회성 말버릇** → 재현 안 됨.

**단계 3 — 하네스 엔지니어링**
- **은유 앵커**: 하네스(harness) = 마구·안전벨트 = 힘 센 놈(AI)을 정해진 방향으로만 쓰게 잡아주는 장치. → "AI를 우리 팀 기준으로 쓰게 잡아주는 것".
- **부품이 아니라 흐름**: 설계 먼저 → 컨텍스트 고정 → 작은 단위 구현 → 품질 확인. (이 "작업 흐름"을 한 장으로. ②덱의 실행 흐름 `USER→Skills→Agent`와는 층위가 다름을 구분.)
- 정의: 좋은 프롬프트를 모으는 게 아니라, **AI가 같은 기준으로 일하게 만드는 문서 구조**를 고정.

### 4-3. 착지 슬라이드 (①의 클라이맥스)
- 세 개념을 한 화면에 겹쳐, 공통분모를 뽑아낸다 → **"결국 남는 능력은 문서(프롬프트)를 쓰는 능력"**.
- 다음 덱 예고: "그 문서가 실제로 어떻게 생겼는지 보자".

- 회수 문장: "그래서 플랫폼별 디테일이 아니라 **`.md` 문서 쓰는 능력**이 남는다" (§1 주장).

**(참고) Antigravity 역할 구분 — 발표자 배경지식(슬라이드엔 안 넣거나 각주):**

| 개념 | 용도 |
|------|------|
| Rules | Agent가 항상 따르는 프로젝트 규칙 |
| Workflows | 사용자가 명시 호출하는 반복 절차 — **여러 skill을 엮는 파이프라인** |
| Skills | 재사용 전문 능력·지식 패키지 (`SKILL.md`, 의미기반 트리거) |
| Task List / Plan | 요청 처리 중 Agent가 생성하는 실행 계획 |

> `workflows`는 **폐기 아님** — 공식 2026 자료도 `.agents/`의 workflow 파일 인식을 설명. `.agents/{rules,workflows,skills}` 구조는 여전히 유효. 핵심 구분: **명령 한 번→정해진 절차 = Workflow / 재사용 전문 능력 = Skill**. 단, 교육에서는 보편 단위(Skill)를 앞세운다.

### 5-6. 보완 필요 (D) — 플랫폼 표면(web/cli/app) & 공통 조작 (신설 1장, ②덱 도입부)
> 요청 취지: 복잡하지 않게 "이런 게 있다" 수준 + 공통 조작 각인.

**(1) 3개 벤더 × 3개 표면 매트릭스**

| 벤더 | Web | CLI | App / IDE |
|------|-----|-----|-----------|
| Anthropic (Claude) | claude.ai | Claude Code | Claude 데스크톱 앱 · IDE 확장 |
| OpenAI (Codex) | chatgpt.com | Codex CLI | ChatGPT 앱 · Codex IDE |
| Google (Antigravity) | Gemini(gemini.google.com) | Antigravity CLI | Antigravity IDE |

**표면별 특징(표면적 수준만):**
- **Web** — 대화·탐색·설계·긴 브레인스토밍에 강함, 파일시스템 직접 접근은 약함
- **CLI** — 실제 파일 생성·수정, git, 헤드리스 자동화(CI/CD)에 강함
- **App/IDE** — GUI 통합·인앱 편의(Agent Manager·브라우저 내장 등) / **발표자 노트: "나는 보통 인앱을 쓴다"**
- (레포 `Harness_Engineering.md` §12-1 "웹 AI vs IDE 에이전트 역할 차이"와 연결)

**(2) 공통 조작 (검증 완료)**
- **`@` = 파일·컨텍스트 언급** — 셋 다 지원 → **공통** (가장 확실)
- **스킬 호출도 셋 다 가능** — 메커니즘의 결만 다름:
  - Claude: 스킬이 슬래시 커맨드로 통합 → `/skill-name`
  - Codex: `/` 커맨드 + 인라인 스킬 `$skill-name`
  - Antigravity: **스킬 = 의미 기반 자동 호출(프롬프트에 이름 지목 시 강제)**, workflows = `/workflow-name`. 스킬을 `/`로 노출하는 흐름도 확산 중(부분적·진화 중)
- **슬라이드 표면은 단순하게**: "스킬/명령은 `/`, 파일은 `@` — 어디서나 통한다". 위 도구별 미묘차는 **발표자 노트로만**.
- **§1 주장 연결**: `/`로 스킬 부르고 `@`로 문서 붙이는 = "결국 AI에게 **문서를 가리키는** 공통 조작" → 문서 쓰기가 핵심이라는 주장과 이어짐

### 5-7. 보완 필요 (E) — 인식 경로 단순화 + 스코프(프로젝트/전역)
> 요청 취지: 경로를 다 나열하지 말고 실무 관례로 좁히되, "전역/특정 설정" 개념은 남긴다.

**(1) 슬라이드 표면 — 딱 두 줄만 명시**
- `프로젝트 루트/.claude/*` (Claude 계열이 인식)
- `프로젝트 루트/.agents/*` (Codex·Antigravity 공용 계열이 인식)
- **발표자 노트**: "다른 경로(`.codex/`, `~/.claude/`, `~/.gemini/config/` 등)도 있지만, **프로젝트마다 상이해서** 나는 보통 프로젝트 루트의 이 두 곳을 쓴다."

**(2) 스코프 개념 — 특정(프로젝트) vs 전역(global)**
- 같은 스킬/설정을 **프로젝트에만** 둘 수도, **전역(사용자 홈 `~`)에 두어 모든 프로젝트에서** 쓸 수도 있다.
- 도구별 대응(슬라이드엔 요약만, 상세는 발표자 노트):

  | 도구 | 프로젝트 스코프 | 전역 스코프 |
  |------|-----------------|-------------|
  | Claude | `<proj>/.claude/…` | `~/.claude/…` |
  | Codex | `<proj>/.agents/skills`·`.codex/skills` | `~/.codex/skills` |
  | Antigravity | `<proj>/.agents/skills` | `~/.gemini/config/skills` |

- 메시지: **"자주 쓰는 건 전역, 프로젝트 특화는 프로젝트에"** — 규모·재사용에 따라 선택.
- §1 주장 연결(약): 어디에 두든 결국 **같은 `.md` 규격** — 위치(스코프)만 다를 뿐이다.

- 날짜·마감기한·기간 설정
- 마감 알림 (브라우저/데스크톱 Notification)
- **`.md` 파일로 내보내기 — 특히 주간보고 형식** (관통 주장 회수 지점)
- 개인용 (공유·동기화 없음)

**기술 스택 (확정)**:

| 계층 | 선택 | 근거 |
|------|------|------|
| 데스크톱 껍데기 | **Electron** | Node.js만 있으면 됨 → 라이브 셋업 안정. Tauri 대비 Rust 툴체인 이슈 없음 → "복잡도 낮게" 원칙 정합 |
| UI | **React + TypeScript** | 웹 표준·친숙도 최상 |
| 저장 | **JSON 파일** (DB 없음) | 사용자가 저장 폴더 지정. 결과물이 파일로 눈에 보임 → 주장 정합 |
| 알림 | Electron Notification API | 별도 인프라 불필요 |
| 빌드·배포 | `electron-builder` → **`.exe` 설치 파일** | 청중에게 나눠줄 수 있는 최종 산출물 |

**저장 구조**:
```
{사용자 선택 폴더}/
├── todos.json           ← 계층 전체 (parentId 방식)
├── weekly-2026-W28.md   ← 내보낸 주간보고
└── ...
```
- 첫 실행: 폴더 선택 다이얼로그(`dialog.showOpenDialog`) → 경로를 `app.getPath('userData')/config.json`에 기억
- 이후 실행: 기억된 폴더 사용. "폴더 변경" 버튼 제공
- 저장 트리거: 편집 시마다 `todos.json` 덮어쓰기 (debounce 300ms)

**주간보고 `.md` 템플릿(핵심)**: 이번 주 완료·진행·다음주 계획을 부모→자식 들여쓰기로 렌더. 이 파일이 **데모의 클라이맥스** — 탐색기 열어서 사용자 폴더 안 `.md` 파일 실물 공개.

### 6-2. 라이브 데모 대본 — 1안 (별도 파일 `1안_라이브데모_대본.md`, 슬라이드 아님)

**4단 흐름 = §1 주장 체현**:

| 단계 | 무엇을 시연 | 관통 주장과의 연결 |
|------|--------------|---------------------|
| ① 환경설정·요구정리 | `superpowers`로 `brainstorming` 스킬 호출 → AI가 요구사항을 캐물어 **설계 `.md`** 를 먼저 만든다 | "질의 능력" + "말이 아니라 문서" — §1 두 축 동시 등장 |
| ② 구현 | 그 설계 `.md`를 근거로 Electron+React 코드 생성. 폴더 선택·저장·알림 동작 | "문서가 산출물의 근거" 실증 |
| ③ 주간보고 `.md` 내보내기 | 앱에서 [주간보고 내보내기] → 사용자 폴더에 `.md` 생성 | **클라이맥스** — 산출물 자체가 문서 |
| ④ 재현 | 코드 폴더 통째로 지우고, **설계 `.md` 하나만 남기고** 재요청 → 다시 같은 앱이 만들어짐 | "문서 있으니 재현된다" — Spine 완결 |

- 시간 예산: 30분 (2.5h 기준). 밀리면 ③까지만, ④는 발표자 노트로 요약.
- **실패 시 롤백**: 미리 커밋해둔 완성본 브랜치로 `git checkout` — 데모용 백업.

### 6-3. 실습 vs 시연 방침
- 기본: **시연 주도 + 초경량 참여 1~2회**(준비된 환경에서 프롬프트 한 줄 직접 입력). 전면 실습은 §8 장비·시간 충족 시만.
