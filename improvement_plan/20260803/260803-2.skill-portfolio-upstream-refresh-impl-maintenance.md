3. adapted runtime과 reference-only principles를 같은 upstream SHA로 원자적으로

4. 기존 로컬 수정 계약과 Codex·Claude 이중 runtime 동작을 보존한다.

   생성한다.

다음 조건을 모두 만족해야 이 계획을 완료로 표시한다.

## 5. 변경 불변식과 승인 게이트

### 5.1 불변식

1. `observed`는 확인 사실이고 `accepted`는 관리자 결정이며 `embedded`는 canonical
   반영 상태다. 세 상태를 한 번에 자동 이동하지 않는다.
2. `ui-ux-pro-max` group의 두 source는 같은 release ref와 SHA를 사용한다.
3. adapted 관계만 실제 runtime 파일을 가질 수 있다. reference 관계는 개념·행동
   영향과 소비자만 기록한다.
4. 현재 로컬 `SKILL.md`의 플랫폼 중립 경로, 범위 확인, 기존 design token 우선,
   승인형 저장 계약은 명시적 설계 변경 승인 없이는 약화하지 않는다.
5. 반입 scripts는 standard library only, no network, no subprocess, no `eval`/`exec`
   조건을 다시 검증한다.
6. protected asset hash 또는 file map이 stage 이후 변하면 promotion을 중단한다.
7. generated projection과 plugin tree를 직접 편집하지 않고 canonical source 및
   builder를 통해 재생성한다.
8. 기존 candidate·promotion·archive는 역사적 증적으로 덮어쓰지 않는다.

### 5.2 승인 게이트

| Gate | 요구 시점 | 승인 없을 때 |
|---|---|---|
| G0 계획 승인 | Phase 0 시작 전 | 읽기 전용 조사만 가능 |
| G1 후보 선택 | `v2.12.0` candidate tree 생성 전 | 관찰 결과만 보존 |
| G2 license/security | stage 전 | `block` 상태, stage 금지 |
| G3 일반 적용 승인 | promotion handoff 전 | `--dry-run`까지만 허용 |
| G4 보호 자산 승인 | scripts/references/data/assets/evals 변경 시 | `--asset-approval-id` 없이 promotion 금지 |
| G5 파괴적 변경 승인 | 삭제·이동·대체 존재 시 | `--destructive-approval-id` 없이 promotion 금지 |

## 7. 구현 Phase

각 Phase는 구현, `impl-verify` 방식의 fresh-evidence 검증, 범위 확인, 독립 commit을
한 묶음으로 끝낸다. 다음 Phase는 직전 Phase 보고와 필요한 승인을 받은 뒤 시작한다.

### Phase 0 — 재기준선과 변경 허용 목록 고정

**목표**: 계획 작성 시점의 관찰 결과가 실행 시점에도 유효한지 확인하고 변경 범위를
고정한다.

작업:

1. branch, HEAD, remote, worktree, 현재 `0.3.0` archive SHA-256을 기록한다.
2. `registry.json`, `lock.json`, `current-skills.json`, UI/UX provenance tree의
   SHA-256을 기록한다.
3. `check_upstreams.py --verify-watched-paths`를 쓰기 없이 다시 실행한다.
4. UI/UX stable release가 `v2.12.0`보다 더 올라갔다면 이 계획을 자동 확장하지 않고
   target ref 변경 승인을 다시 받는다.
5. exact changed-path allowlist와 historical-preserve 목록을 만든다.

검증:

```powershell
git status --short --branch
git rev-parse HEAD
git remote -v
Get-FileHash -Algorithm SHA256 plugins/harness-kit-0.3.0.zip
python maintainer/skills/skill-portfolio-maintainer/scripts/check_upstreams.py --verify-watched-paths
python maintainer/skills/skill-portfolio-maintainer/scripts/validate_registry.py
git diff --check
```

완료 기준: 기준선 clean, target ref 승인, 실패 source에 state write 없음, 변경 허용
목록 확정.

권장 commit: `docs(plan): baseline skill portfolio upstream refresh`

### Phase 1 — 관찰값 분류와 차단 해소

**목표**: update, no-op, reference review, retry-required를 source별로 분리한다.

작업:

1. UI/UX group 두 source를 source-filtered check로 다시 확인한다.
2. 성공한 결과만 `--write-observed`로 lock의 `observed`에 기록한다. accepted·embedded는
   변경하지 않는다.
3. `im-not-ai`를 별도로 재조회한다. 403이 반복되면 `stale-preserved`로 보고하고
   기존 pin을 유지한다.
4. `openai-codex-skill-creator`의 두 exact path를 이전 증적과 비교하고
   `custom-skill-design` 행동 변화 필요 여부를 보고한다.

## 8. 위험과 rollback

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| source head와 watched path 혼동 | branch 이동만으로 자동 갱신 제안 | exact path·semantic diff를 별도 기록 |
| relationship group 반쪽 적용 | runtime/principles ref·SHA 불일치 | 둘 다 되돌리고 같은 commit으로 재검토 |
| 로컬 adapted 계약 유실 | upstream SKILL.md로 단순 덮어쓰기 | 3-way merge, runtime-preview eval, G6 차단 |
| reference 파일 반입 | consumer skill에 upstream 문구·파일 복사 | reference diff 제거, 로컬 계약으로 재서술 |
| license 변화 누락 | LICENSE hash 불일치 | `block-license`, 승격 중단 |
| 보호 script 위험 증가 | network/subprocess/eval/exec 또는 새 write path | `block-security` 또는 별도 설계·승인 |
| upstream 삭제가 로컬 삭제로 전파 | `destructive_changes` 누락 | G5 전까지 삭제 금지 |
| stage 후 candidate 변조 | candidate/tree hash mismatch | 폐기 후 다시 stage |
| 403을 최신 상태로 오판 | im-not-ai 관찰값을 성공으로 write | last accepted 보존, 인증/시간 경과 후 재조회 |
| 기존 artifact 덮어쓰기 | `0.3.0` zip hash 변화 | build 중단, 이전 commit에서 archive 복구 |
| generated tree 직접 수정 | source/projection drift | generated diff 제거 후 builder 재실행 |
| 실제 앱 검증 없이 release-ready | 자동 PASS만 존재 | `not-release-ready` 유지 |

promotion handoff 이후 문제가 발견되면 먼저 비파괴 보고서를 만든다.

```powershell
python maintainer/skills/skill-portfolio-maintainer/scripts/rollback_upstream.py --candidate-id ui-ux-pro-max-v2.12.0
```

이 명령은 자동으로 파일을 삭제하거나 되돌리지 않는다. 보고서와 현재 lock을 검토한
뒤 일반 Git review로 canonical 변경을 되돌리고 plugin을 재생성한다.

## 9. impl downstream handoff ledger

이 계획의 roadmap index는 사용자 애플리케이션의 `.docs` roadmap이 아니라 저장소
유지관리 정본인 `improvement_plan/README.md`다. 각 Phase는 다음 상태를 갱신한다.

| Phase | reuse-scan | verify | 주요 증적 |
|---|---|---|---|
| 0 기준선 | `required` | clean baseline·read-only check | HEAD, archive hash, check JSON |
| 1 관찰 분류 | `required` | observed-only diff | source별 check 결과 |
| 2 후보 구성 | `required` | tree/file-map completeness | candidate, source/runtime tree hash |
| 3 영향 심사 | `required` | license/security/asset gate | review·asset report |
| 4 stage | `required` | candidate/tree immutability | stage-report, dry-run |
| 5 promotion | `required` | approval ID·handoff 경계 | promotion JSON |
| 6 canonical 적용 | `required` | group·skill eval | registry/lock/provenance diff |
| 7 plugin handoff | `required` | projection/archive determinism | build·inventory evidence |
| 8 통합 회귀 | `required` | fresh full regression | release regression·smoke |
| 9 최종 경계 | `not-applicable` (새 구현 자산 없음) | plan/diff/publish gate | Phase ledger·git status |

`impl-verify`는 보고 전용으로 실행하며 검증 중 자동 수정하지 않는다. 실패는 원인과
영향 범위를 보고하고 해당 Phase를 완료로 표시하지 않는다.
