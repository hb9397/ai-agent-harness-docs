## 1. 결론과 권장 진행 방향

2026-08-03에 관리자용 `skill-portfolio-maintainer`를 쓰기 없는 실제 점검 모드로
실행했다. 레지스트리와 자체 eval은 정상이며 canonical skill, accepted/embedded
lock, plugin runtime에는 변경이 발생하지 않았다.

이 계획은 서로 독립적으로 승인·구현·rollback할 수 있는 두 작업 Track으로 나눈다.
Track A는 업스트림 최신성 갱신이고, Track B는 프로젝트에 한 번 설치한 하네스 계약이
`harness-kit` runtime 호출 없이도 다른 플러그인·스킬·일반 AI 도구의 산출물을 같은
설정과 `.docs` 정본 위치로 유도·강제하게 만드는 작업이다. 두 Track은 commit을
분리하고, 최종 plugin build만 양쪽의 수용 결과를 모아 한 번 수행한다.

Track A의 점검 결과 다음 두 후속 검토가 필요하다.

1. **주 실행 트랙 — UI/UX Pro Max**
   - 현재 accepted·embedded: `v2.11.3` /
     `4857a2c5ef989794751a0f66b8545a4a49566286`
   - 현재 원격 stable: `v2.12.0` /
     `14ddef5c05e52d7c253b8f0129de7bcd1045ae5b`
   - `ui-ux-pro-max-runtime`의 adapted 관계와
     `ui-ux-pro-max-principles`의 reference 관계를
     `relationship_group=ui-ux-pro-max` 하나로 원자적으로 검토한다.
2. **차단 해소 트랙 — im-not-ai**
   - 원격 조회가 GitHub rate limit `HTTP 403`으로 실패했다.
   - 실패 상태에서는 `v2.3.0` pin을 보존하며 관찰값·accepted·embedded를
     변경하지 않는다. 인증된 재조회나 rate limit 해소 후 별도로 판정한다.

`openai-codex-skill-creator`는 저장소 branch head가 이동했으나 현재 관계는
reference-only이고 accepted/embedded 상태가 없다. 정확한 watched path 중
`SKILL.md`의 마지막 변경 commit은 기존과 같고 `references/openai_yaml.md`는 새
path-level commit이 확인됐으므로, `custom-skill-design`에 영향을 주는 의미 변화가
있는지만 별도 diff로 검토한다. 자동 반입이나 자동 계약 변경은 하지 않는다.

Track B의 핵심 원칙은 플러그인 이름 allowlist가 아니라 **산출물의 의미와 프로젝트의
현행 정본 계약**으로 경로를 결정하는 것이다. Harness Kit은 이 계약을 생성·갱신하는
도구일 뿐, 생성 후 라우팅의 runtime 의존성이 아니다. 따라서 루트 `AGENTS.md`, 최소
`CLAUDE.md` bridge, 앱별 `artifact-output-routing-instruction.md`와 호스트가 공식
지원하는 경우에만 설치되는 write hook을 portable project-owned bundle로 관리한다.
초기화되지 않은 프로젝트에 아무 도구도 없이 파일이 생긴다고 가정하지 않는다.
대신 플러그인 없이도 같은 파일을 수동 적용할 수 있는 bundle·설치 절차와 검증 명령을
제공한다.

Layer 3의 host 설정은 공유하지 않는다. Claude는 `.claude/settings.json`, Codex는
`.codex/hooks.json`을 사용하고 각 adapter가 서로 다른 stdin·deny schema를 처리한다.
`harness-setup`이 설치·갱신·제거를 소유하고, `harness-bootstrap`은 무문서 프로젝트에서
같은 setup 계약으로 handoff하며, `context-doc`은 의미·형식 routing instruction을
소유한다.

## 3. 목표와 완료 정의

### 3.1 목표

1. 실제 관찰값과 accepted·embedded·packaged 상태를 섞지 않는다.
2. UI/UX Pro Max `v2.12.0`을 현재 `v2.11.3`과 파일·행동·권리·보안 단위로 비교한다.
3. adapted runtime과 reference-only principles를 같은 upstream SHA로 원자적으로
   승인하거나 함께 보류한다.
4. 기존 로컬 수정 계약과 Codex·Claude 이중 runtime 동작을 보존한다.
5. 보호 자산과 삭제·이동을 일반 승인과 분리한다.
6. 승격 handoff 전후에 canonical source, projection, plugin artifact의 경계를
   명확히 유지한다.
7. 변경이 수용되면 immutable `0.3.0` artifact를 보존하고 영향도에 맞는 새 버전을
   생성한다.
8. 외부 플러그인·스킬·일반 AI 도구가 생성하는 산출물을 생산자 이름이 아니라 의미로
   분류해 기존 단일·복수 애플리케이션 `.docs` 정본 경로로 라우팅한다.
9. Harness Kit으로 한 번 생성하거나 portable bundle로 수동 적용한 프로젝트 설정은
   이후 `harness-kit` runtime 호출 없이 독립적으로 동작한다.
10. 프로젝트의 기존 `README`, `AGENTS.md`, 앱별 routing instruction과 사용자 확장을
    generic default보다 우선하며 update mode에서 보존한다.
11. Claude와 Codex의 공식 `PreToolUse` hook을 서로 다른 설정·입출력 schema의
    독립 adapter로 구현한다. 두 host가 `.claude` 설정을 공유한다고 가정하지 않는다.
12. 외부 플러그인의 자체 위치·Markdown 구조가 Harness Kit과 달라도 먼저 canonical
    format으로 직접 생성하도록 지시하고, 고정 형식은 `.docs/_inbox/`에 격리한 뒤
    승인형 normalize/promote 절차로 기존 정본에 병합한다.
13. Harness Kit의 사용자 스킬 19종과 관리자 스킬 3종 전체를 중앙 산출물 계약과
    대조한다. user managed-project-output producer는 같은 위치·형식·승인·handoff
    계약을 따르고 manager producer는 사용자 `.docs`를 쓰지 않는 경계를 유지한다.

### 3.2 완료 정의

다음 조건을 모두 만족해야 이 계획을 완료로 표시한다.

1. 모든 source의 관찰 결과가 `fresh`, `stale-preserved`, `unsupported-tracking`,
   `blocked` 중 하나로 근거와 함께 분류된다.
2. UI/UX Pro Max `v2.11.3..v2.12.0` 파일 diff와 exact watched path 증적이 있다.
3. `ui-ux-pro-max-runtime`과 `ui-ux-pro-max-principles`가 같은 ref·SHA·lifecycle을
   사용하거나 둘 다 기존 accepted 상태를 유지한다.
4. runtime adapted 관계의 upstream source tree와 local runtime preview가 각각
   실제 파일 tree 및 SHA-256으로 고정된다.
5. reference 관계는 upstream 파일을 로컬 consumer skill에 복사하지 않는다.
6. license hash·NOTICE·file-map이 검토되고 license 변화가 있으면 승격이 차단된다.
7. scripts·references·data·assets·evals의 추가·수정·삭제가 자산 영향 보고서에
   빠짐없이 기록된다.
8. 일반 승인, 보호 자산 승인, 파괴적 변경 승인이 필요한 경우 각각 별도 ID를 가진다.
9. `stage_upstream.py`가 canonical skill과 embedded lock을 변경하지 않은 채 실제
   source/runtime tree hash를 기록한다.
10. `promote_upstream.py --dry-run`과 실제 handoff가 동일한 candidate hash 및 tree
    hash를 검증한다.
11. canonical 적용은 promotion handoff 이후 별도 Phase에서만 수행된다.
12. 사용자 스킬 수 19, 관리자 스킬 수 3, plugin agent 수 0을 유지한다.
13. Codex·Claude projection과 plugin payload가 canonical source와 일치한다.
14. 이전 `plugins/harness-kit-0.3.0.zip`의 SHA-256이 변하지 않는다.
15. 전체 registry·skill eval·plugin 회귀 검증이 통과한다.
16. push·tag·release는 별도 명시적 요청 전까지 수행하지 않는다.
17. single/multi-app에서 design, plan, context, instruction, prototype, design-system,
    source, report, temporary artifact가 의미별 canonical 경로로 결정된다.
18. Superpowers 등 외부 도구의 `docs/superpowers/**`나 루트 `design-system/` 같은 자체
    기본 경로는 프로젝트 계약으로 대체되며 플러그인 이름 디렉터리를 만들지 않는다.
19. portable project-owned bundle의 생성 파일, 수정 파일, 로컬 설치 파일과 공유용
    원본이 구분되고, Harness Kit 제거 후에도 동일한 설정·경로 계약을 재검증할 수 있다.
20. update mode는 managed marker 밖의 사용자 내용과 기존 routing 확장을 byte-preserve
    하고, 실제 쓰기 전에 diff proposal과 생성·수정 파일 목록을 승인받는다.
21. 새 `.docs` Markdown은 정확한 대상 경로에 대한 1회성 승인만 통과하고 승인 marker는
    소비된다. 기존 파일 수정은 통과하며 경로 traversal·대소문자·구분자 우회를 막는다.
22. Claude는 `.claude/settings.json`과 `.claude/hooks/**`, Codex는
    `.codex/hooks.json`과 `.codex/hooks/**`를 각각 설치한다. 공통 정책만
    `.docs/harness/**`에 두고 host adapter를 섞지 않는다.
23. Codex project `.codex` layer의 trust와 hook definition hash review를 완료하고,
    신규·변경 hook은 `/hooks`에서 재승인되기 전까지 강제가 활성화됐다고 표시하지 않는다.
24. 외부 Markdown 문서는 UTF-8·기존 newline 보존·artifact별 필수 섹션·managed merge
    규칙을 거쳐 canonical 정본에 반영된다. HTML·JSON·YAML·이미지 등 고정 형식은
    source/prototype 계약에 해당하지 않으면 `_inbox` 원본과 normalization provenance를
    남긴다.
25. `harness-setup` 적용 후 plugin/cache를 제거한 상태에서도 Codex·Claude 각각의
    instruction + hook 조합이 동일한 manifest·경로·format 판정을 낸다.
26. 최소 16개 semantic routing·format normalization·update·host hook·Windows·분리
    Git topology eval, 사용자 19 + 관리자 3 contract coverage와 전체 plugin 회귀
    검증이 통과한다.

## 5. 변경 불변식과 승인 게이트

### 5.1 불변식

1. `observed`는 확인 사실이고 `accepted`는 관리자 결정이며 `embedded`는 canonical
   반영 상태다. 세 상태를 한 번에 자동 이동하지 않는다.
2. `ui-ux-pro-max` group의 두 source는 같은 release ref와 SHA를 사용한다.
3. adapted 관계만 실제 runtime 파일을 가질 수 있다. reference 관계는 개념·행동
   영향과 소비자만 기록한다.
4. 현재 로컬 `SKILL.md`의 플랫폼 중립 경로, 범위 확인, 기존 design token 우선,
   승인형 저장 계약은 명시적 설계 변경 승인 없이는 약화하지 않는다.
5. 반입 scripts는 standard library only, no network, no subprocess, no `eval`/`exec`
   조건을 다시 검증한다.
6. protected asset hash 또는 file map이 stage 이후 변하면 promotion을 중단한다.
7. generated projection과 plugin tree를 직접 편집하지 않고 canonical source 및
   builder를 통해 재생성한다.
8. 기존 candidate·promotion·archive는 역사적 증적으로 덮어쓰지 않는다.
9. 프로젝트 내부의 기존 README·AGENTS·routing instruction이 generic template보다
   우선하며 managed marker 밖의 내용은 수정하지 않는다.
10. 외부 생산자는 이름이 아니라 산출물 의미로 분류한다. 알 수 없는 생산자도
    plugin-named directory를 만들지 않는다.
11. 프로젝트가 이미 선택한 prototype 공용/앱별 정책과 app context 경로를 감지해
    보존하며 single/multi default를 무조건 재적용하지 않는다.
12. Claude와 Codex write hook은 각 host의 공식 schema로 별도 생성하고, local
    installed config의 절대 경로와 `.docs` 공유 원본을 구분한다. `.claude`와 `.codex`
    설정 파일을 상호 복사하지 않는다.
13. 승인 marker는 승인된 normalized path와 정확히 일치해야 하며 한 번 성공 또는
    취소 후 재사용할 수 없다.
14. root가 비-Git이고 `.docs` 및 앱들이 각각 별도 Git 저장소인 topology를 정상으로
    지원하며 Git 명령을 잘못된 상위 root에 강제하지 않는다.
15. 공통 core는 normalized artifact decision만 반환한다. Claude·Codex adapter가
    host별 stdin을 공통 request로 바꾸고 host별 deny/allow 응답을 생성한다.
16. 외부 artifact의 original format은 provenance와 hash를 보존한다. canonical merge는
    필수 필드가 충족되고 사용자 승인과 idempotency 검증이 끝난 뒤에만 수행한다.
17. 사용자 스킬 19종과 관리자 스킬 3종 중 파일 쓰기 가능성이 있는 스킬은 중앙
    contract에 선언돼야 한다. 누락·unknown write capability 또는 manager의 user
    `.docs` write는 validator 실패다.

## 8. Track B — Harness Kit runtime 비종속 산출물 라우팅 구현 Phase

### 8.1 canonical 의미 라우팅 표

Harness Kit 자체와 알려진 외부 plugin만 나열하는 allowlist를 만들지 않는다. 생산자와
관계없이 요청의 주된 산출물 의미를 다음 순서로 분류한다. 프로젝트에 이미 더 구체적인
README·AGENTS·routing instruction이 있으면 해당 규칙이 이 표보다 우선한다.

| 산출물 의미 | 단일 애플리케이션 | 복수 애플리케이션 | 기본 동작 |
|---|---|---|---|
| requirements, design, architecture, brainstorming, PRD, RFC, spec | `.docs/context-base/DESIGN.md` | `.docs/{app}/context-base/DESIGN.md` | 새 별도 spec 폴더를 만들지 않고 정본을 갱신 |
| implementation plan, task, checklist | `.docs/impl-doc/{user}/{feature}.md` | `.docs/{app}/impl-doc/{user}/{feature}.md` | 기존 filename convention·roadmap index 우선 |
| app context | `.docs/context.md` 또는 감지된 현행 정본 | `.docs/{app}-context.md` | 기존 canonical이 있으면 그 경로 보존 |
| instruction | `.docs/instruction/{topic}-instruction.md` | `.docs/{app}/instruction/{topic}-instruction.md` | root `AGENTS.md`는 색인·요약만 유지 |
| validation prototype | 감지된 `.docs/prototype/**` 공용 정책 또는 앱 정책 | `.docs/prototype/**` 또는 `.docs/{app}/prototype/**` 중 현행 정책 | 신규 생성 전에 공용/앱별 소유권 확인 |
| reusable design system | `.docs/design-system/{project-slug}/` | `.docs/{app}/design-system/{project-slug}/` | validation prototype과 분리 |
| implementation, test, build/runtime config | 실제 source tree | 선택한 app source tree | `.docs`에 제품 코드를 만들지 않음 |
| review, audit, verification | chat/report-only | 선택 앱 범위의 chat/report-only | 명시적 저장 요청 없이는 파일 없음 |
| temporary input, log, screenshot | `.docs/_inbox/` | 공용 `.docs/_inbox/` | 정본으로 승격하기 전 임시 입력임을 표시 |

adapter 최소 계약은 다음과 같다.

- Superpowers brainstorming/spec 계열은 `DESIGN.md`, writing-plans/task 계열은
  `impl-doc`으로 라우팅한다. `docs/superpowers/specs`와 `docs/superpowers/plans`는
  생성하지 않는다.
- UI/UX 계열 도구의 검증용 UI는 prototype, 재사용 가능한 시각 규칙은
  design-system으로 분리한다. 루트 `design-system/` 기본값은 사용하지 않는다.
- Caveman·Ponytail처럼 태도·문체·검토 방식만 바꾸는 plugin은 별도 산출물을 만들지
  않는다.
- unknown plugin은 이름이 아니라 위 의미표로 분류하고 `{plugin-name}/` 폴더를 만들지
  않는다. 의미가 둘 이상이거나 대상 app이 불명확하면 쓰기 전에 한 번 확인한다.

### 8.2 외부 산출물 형식 정규화 계약

위치가 맞더라도 Harness Kit 정본 형식과 병합 규칙을 충족하지 않으면 canonical로
간주하지 않는다. 외부 producer에는 먼저 canonical 형식으로 직접 출력하도록 Layer 1·2
지침을 제공한다. producer가 형식을 제어할 수 없을 때만 `_inbox` normalize/promote
흐름을 사용한다.

| 입력 형식·상황 | 수집 위치 | canonical 반영 |
|---|---|---|
| Harness Kit 계약을 따르는 Markdown | 8.1의 canonical path | 필수 섹션·링크·owner 검증 후 기존 정본 merge |
| 다른 heading·frontmatter의 Markdown/MDX/TXT/RST/AsciiDoc | `.docs/_inbox/{artifact-bundle-id}/` | UTF-8 Markdown proposal로 정규화하고 G12 승인 후 merge |
| 외부 plugin의 JSON/YAML 구조화 문서 | `.docs/_inbox/{artifact-bundle-id}/` | schema mapping과 필드 손실 0건을 검증한 경우에만 Markdown 정본 또는 선언된 machine-readable companion으로 승격 |
| 검증용 HTML/CSS/JS | 감지된 공용/앱별 prototype 경로 | prototype bundle 계약과 asset 상대 링크를 검증 |
| 실제 build/runtime JSON·YAML·config | 선택 app source tree | 문서 normalizer를 적용하지 않고 source owner에게 인계 |
| 이미지·PDF·binary 참고자료 | `.docs/_inbox/{artifact-bundle-id}/` | 원본 hash·출처를 보존하고 정본에는 링크·요약만 승인 반영 |
| review/audit 임시 보고 | chat-only | 명시적 저장 요청이 있을 때만 선택 canonical report 계약 적용 |

새 canonical Markdown은 UTF-8·LF를 기본으로 하되 기존 파일 갱신은 현재 newline을
보존한다. artifact별 필수 형식은 중앙 contract에 선언한다.

- `DESIGN.md`: 기존 design-doc section ID·결정·acceptance criteria를 보존하고 외부
  PRD/RFC/spec를 중복 파일로 만들지 않고 충돌 proposal로 병합한다.
- impl plan: `impl-doc`/`impl-fe-be-doc`의 Phase, task ID, exact path, verification,
  roadmap index, reuse-scan·impl-verify handoff를 충족해야 한다.
- instruction: scope, precedence, canonical path, producer adapter, validation과 managed
  marker를 가진다.
- prototype/design-system: 기존 producer의 bundle manifest·asset link·검증 계약을
  따른다.
- source mutation: 문서 형식으로 변환하지 않고 선택 app source·owner·test 계약을
  따른다.

각 `_inbox` bundle에는 `artifact-manifest.json`을 두어 source producer, original path,
media type, SHA-256, target artifact class/app, normalization status, proposal hash,
approval ID를 기록한다. normalize는 새 병렬 정본을 만들지 않고 기존 canonical
문서를 찾은 뒤 3-way merge proposal을 만든다. 같은 original/proposal hash 재실행은
동일 결과를 내며 중복 승격하지 않는다.

### 8.3 보장 범위와 우회 경계

| 실행 경로 | 적용 수준 | 판정 |
|---|---|---|
| Codex `apply_patch`·local function·관찰 가능한 shell/MCP | AGENTS + Codex `PreToolUse` | 위치 차단·정정, format proposal 적용 가능 |
| Claude Write/Edit와 관찰 가능한 local tool | CLAUDE bridge + Claude `PreToolUse` | 위치 차단·정정, format proposal 적용 가능 |
| 지침을 읽는 외부 plugin skill | Layer 1·2 의미·형식 계약 | canonical 직접 생성 또는 `_inbox` normalization |
| 고정 output의 외부 plugin | wrapper/adapter가 있는 경우 | `_inbox` 수집 후 승인형 승격 |

### Phase B4 — Claude·Codex dual-host write guard와 1회성 승인 보안 구현

**목표**: 두 host의 공식 `PreToolUse`를 별도 adapter로 구현해 canonical 위치 이탈,

공통 core 계약:

1. adapter가 넘긴 host-neutral request에서 operation, tool, cwd, target path,
   artifact class, media type과 proposed content/hash를 판정한다.
2. absolute/relative path, `.`·`..`, `/`·`\\`, drive-letter case, Unicode/UTF-8을
   normalize한 뒤 path-segment 경계로 project containment를 판정한다.
3. root `AGENTS.md`·`CLAUDE.md`, 승인된 app source, `.docs/_inbox/**`, project 밖

4. project 안의 잘못된 managed artifact 경로는 block하고 8.1로 계산한 올바른 경로와
   8.2 format action(`direct`, `normalize-to-inbox`, `source-handoff`)을 반환한다.
5. 기존 canonical file edit은 통과시킨다. 새 `.docs` file 또는 bundle은 명시 승인된
   normalized target path와 marker payload가 정확히 일치할 때 한 번만 통과시키고
   marker를 원자적으로 소비한다.
6. marker는 TTL, nonce, target path, operation, content/proposal hash를 가지며 sibling
   path·directory-wide·내용 변경 재사용을 허용하지 않는다.
7. Markdown 계열은 위치와 format proposal을 모두 검사한다. 비 Markdown은 app source,

1. `.codex/hooks.json`의 `PreToolUse`에 `Edit|Write|Bash` matcher와

## 9. 위험과 rollback

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| source head와 watched path 혼동 | branch 이동만으로 자동 갱신 제안 | exact path·semantic diff를 별도 기록 |

| reference 파일 반입 | consumer skill에 upstream 문구·파일 복사 | reference diff 제거, 로컬 계약으로 재서술 |
| license 변화 누락 | LICENSE hash 불일치 | `block-license`, 승격 중단 |
| 보호 script 위험 증가 | network/subprocess/eval/exec 또는 새 write path | `block-security` 또는 별도 설계·승인 |
| upstream 삭제가 로컬 삭제로 전파 | `destructive_changes` 누락 | G5 전까지 삭제 금지 |
| stage 후 candidate 변조 | candidate/tree hash mismatch | 폐기 후 다시 stage |

| generated tree 직접 수정 | source/projection drift | generated diff 제거 후 builder 재실행 |
| 실제 앱 검증 없이 release-ready | 자동 PASS만 존재 | `not-release-ready` 유지 |

| prototype 소유권 불일치 | 공용·앱별 prototype이 동시에 생김 | 기존 manifest·routing instruction 감지 후 하나를 정본으로 유지 |

## 10. impl downstream handoff ledger

이 계획의 roadmap index는 사용자 애플리케이션의 `.docs` roadmap이 아니라 저장소

|---|---|---|---|
| 0 기준선 | `required` | clean baseline·read-only check | HEAD, archive hash, check JSON |
| 1 관찰 분류 | `required` | observed-only diff | source별 check 결과 |
| 2 후보 구성 | `required` | tree/file-map completeness | candidate, source/runtime tree hash |
| 3 영향 심사 | `required` | license/security/asset gate | review·asset report |
| 4 stage | `required` | candidate/tree immutability | stage-report, dry-run |
| 5 promotion | `required` | approval ID·handoff 경계 | promotion JSON |
| 6 canonical 적용 | `required` | group·skill eval | registry/lock/provenance diff |
| 7 plugin handoff | `required` | projection/archive determinism | build·inventory evidence |
| 8 통합 회귀 | `required` | fresh full regression | release regression·smoke |
| 9 최종 경계 | `not-applicable` (새 구현 자산 없음) | plan/diff/publish gate | Phase ledger·git status |
| B0 routing 기준선 | `required` | host facts·case read-only·failure fixture | capability 판정·topology·hash |
| B1 portable schema | `required` | schema·bundle 경로·cache 비수정 | manifest·`-Plan` diff |
| B2 setup 흐름 | `required` | initial/update/manual·idempotency | created/modified/unchanged ledger |
| B3 의미·형식·producer | `required` | path/format parity·19종 coverage | adapter·normalization·inventory eval |
| B4 dual-host guard | `required` | host schema·path·marker·trust security | Claude/Codex fixture·install/uninstall hash |
