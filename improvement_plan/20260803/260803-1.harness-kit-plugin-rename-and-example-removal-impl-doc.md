## 1. 목적과 결정 사항

이 계획은 선행 사용자 스킬 정비와 두 개의 후속 파괴적 변경을 안전하게 수행하기
위한 작업 지침이다.

1. `pre-commit` 스킬을 제거하고 `commit` 스킬을 Codex·Claude의 명시적 Git 커밋
   행동 계약에 맞게 강화한다.
2. `.user-docs/Skill_Upstream_Update_Policy.md`,
   `.user-docs/Imported_Skill_Provenance.md`,
   `.user-docs/External_Skill_References.md`의 규범·현황·증적을 누락 없이
   `.user-docs/Skill_Upstream_Governance.md` 하나로 통합한다.
3. 현재 `ai-agent-harness` 플러그인의 설치 정체성을 `harness-kit`으로 변경한다.
4. marketplace 식별자를 `ai-agent-harness`에서 `hb9397`로 변경한다.
5. Git remote와 plugin provenance의 repository URL을 `hb9397/harness-kit`으로 정합화한다.
6. 새 로컬 checkout 기준 경로 `C:/Plugin_Workspace/harness-kit`을 사용하고
   machine-specific 절대 경로를 생성 metadata에서 제거한다.
7. 루트 `example/`을 별도 외부 저장소 없이 현재 저장소에서 제거하고, plugin payload가
   참조하는 `skills/**/example(s)` 보호 자산은 유지한다.
8. `impl-doc`·`impl-fe-be-doc`은 구현계획서를 만들기 전에 사용자·앱·저장소 토폴로지와
   `../impl-doc/{사용자 식별}/` 아래의 `design-roadmap` 위치를 먼저 식별하고,
   항상 `*-roadmap-impl-index.md`를 선행 생성·예약·검증한다.
9. 산출물을 생성하거나 변경하는 모든 사용자·관리자 스킬을 단일/복수 앱 범위로
   분류하고, 공용 `@instruction`과 machine-readable 계약 매니페스트를 통해
   산출물 위치·소유권·승인·handoff를 일관되게 관리한다.

### 1.1 이름 선정 이유

`harness-kit`을 선택한다. 짧고 kebab-case 검증 규칙에 맞으며, 선행 `pre-commit`
제거 후 19개 사용자
스킬이 제공하는 설계·구현·검증·문서화 흐름을 특정 모델이나 한 가지 산출물에
가두지 않는다.

| 후보 | 판단 |
|---|---|
| `harness-kit` | **선정**. 범용적이고 설치 표면이 짧으며 확장 가능 |
| `project-harness` | 의미는 명확하지만 일반 명사 조합이라 브랜드 식별성이 약함 |
| `workflow-harness` | workflow에 치우쳐 문서·품질·스킬 포트폴리오를 충분히 표현하지 못함 |
| `agent-workbench` | IDE·실험 도구로 오해할 가능성이 있음 |

### 1.2 호환성 정책

plugin ID와 qualified install 문자열은 사용자 설치 계약이므로 이번 변경은 공개
설치 표면의 breaking change다. `0.2.2`의 manifest, archive, tag를 덮어쓰지 않고
`0.3.0`으로 승격한다. 기본 정책은 별도 legacy alias를 만들지 않는 hard cutover다.

기존 사용자는 다음 순서로 이동한다.

```text
기존 ai-agent-harness@ai-agent-harness 제거
→ marketplace hb9397 갱신
→ harness-kit@hb9397 설치
→ 새 세션에서 skill 호출 확인
```

legacy alias를 병행하면 두 plugin ID와 두 cache 경로를 계속 검증해야 하므로 이번
계획에는 포함하지 않는다. alias가 필요해지면 별도 호환성 계획으로 분리한다.

## 3. 기준선과 영향 범위

### 3.1 현재 플러그인 정본과 repository identity

이름은 다음 정본과 생성물에 중복되어 있다. 문자열 전역 치환을 하지 않고 정본을
먼저 수정한 뒤 생성기를 통해 산출물을 재생성한다.

| 계층 | 현재 위치/값 | 목표 조치 |
|---|---|---|
| source constant | `maintainer/skills/harness-plugin-maintainer/scripts/plugin_common.py`의 `PLUGIN_ID`·`PLUGIN_ROOT_REL` | `harness-kit`, 파생 root |
| builder constant | `build_plugin.py`의 `MARKETPLACE_NAME` | `hb9397` |
| repository constant | `build_plugin.py`의 `REPOSITORY_URL` | `https://github.com/hb9397/harness-kit` |
| Git remote | `.git/config`의 `remote.origin.url` | `https://github.com/hb9397/harness-kit.git` |
| manager skill 정본 | `maintainer/skills/harness-plugin-maintainer/**` | 실제 사용자 plugin ID만 새 이름으로 갱신 |
| manager projection | `.agents/skills/**`, `.claude/skills/**` | sync generator로 재생성 |
| plugin runtime | `plugins/ai-agent-harness/**` | builder로 `plugins/harness-kit/**` 재생성 |
| marketplace | `.agents/plugins/marketplace.json`, `.claude-plugin/marketplace.json` | builder 생성 결과 확인 |
| release evidence | `maintainer/plugin/{release,cli-smoke,install-verification}.*` 등 | 새 ID·qualified ID·archive 반영 |
| 사용자 문서 | `README.md`, `.user-docs/**` | 설치·호출·업데이트·제거 명령 갱신 |

현재 `0.2.2` 기준 archive SHA-256은 다음과 같이 보존한다.

```text
plugins/ai-agent-harness-0.2.2.zip
016be105eaebf46f164641946c1705edbf1b70bed7a3bf4aff661a6e0814d27c
```

현재 checkout 이동은 `.git/config`에 `core.worktree`가 없으므로 Git object와
branch history에 영향을 주지 않는다. 다만 `generated_marker()`와 internal
upstream registry의 source URL에 남은 `D:/Dev_Workspace/ai-agent-harness-docs`는
machine-specific 값이므로 새 checkout 기준에 맞추거나 stable repository URL로
정규화해야 한다. build determinism을 위해 새 `C:/Plugin_Workspace/harness-kit`
절대 경로를 다른 generated artifact에 추가하지 않는다.

### 3.2 루트 example 자산

삭제 전 root `example/`은 다음 11개 파일이었으며, 플러그인 runtime에 직접 포함되는
정본이 아니었다. 파일 목록·내용·SHA-256은 `maintainer/inventory/
example-externalization-baseline.json`에 보존한다.

```text
example/README.md
example/context-doc--AGENTS.md
example/context-doc--CLAUDE.md
example/context-doc--architecture-instruction.md
example/design-doc--ACRO-BE.md
example/design-doc--ACRO-FE.md

example/impl-doc--selector-recovery.md
example/impl-fe-be-doc--ACRO.md
```

Phase 2 source snapshot 기준 총 크기는 225,213바이트였고, pre-Phase 1의
225,227바이트 snapshot은 baseline JSON의 `previous_snapshot`으로 보존한다.
`example/README.md`는 독립 예제 인덱스였으며, 현재 live 문서에서 root `example/`을
직접 링크하는 참조는 확인되지 않았다. 따라서 plugin runtime 동작에는 직접 영향이
없지만, 저장소 clone 사용자의 학습·수동 검증 자료가 사라지는 문서/운영 영향은
삭제 승인과 함께 수용한다.

삭제하지 말아야 할 별도 자산은 다음과 같다.

```text
skills/commit/examples/**
skills/create-prototype/examples/**
skills/design-prototype-docs/example/**
```

이 경로들은 plugin payload 안에서 skill 실행이 참조하는 보호 자산이므로 root
`example/` 삭제와 함께 삭제하거나 이동하지 않는다. 외부 examples 저장소는 만들지
않으며, root 예제의 복구가 필요하면 Git history와 baseline hash를 사용한다.

### 3.3 `commit-workflow` 행동 기준과 upstream/reference 정책

`commit`을 특정 외부 스킬의 복제본으로 관리하지 않는다. Codex·Claude의 공식 Git
동작에서 확인되는 공통 행동과 이 저장소의 명시적 local policy를
`commit-workflow`라는 behavior contract로 관리한다. 공식 제품이 공개하지 않은
세부 알고리즘은 제품 보장으로 표현하지 않고 `local-policy` 또는
`runtime-observation`으로 분리한다.

공식 관찰 출처는 다음과 같다.

| source id | 공식 기준 | 추적 방식 |
|---|---|---|
| `openai-codex-commit-behavior` | Codex 기본 지침·AGENTS.md·approval/sandbox·review·customization 문서 | 문서 URL + watched path commit SHA + 관찰한 `codex-cli` 버전 |
| `anthropic-claude-code-commit-behavior` | Claude Code headless commit 예시·built-in Git instructions·permission·hooks·attribution·changelog | 문서 URL + checked_at + 정규화 content hash + 관찰한 Claude Code 버전 |
| `conventional-commits` | Conventional Commits 1.0.0 메시지 문법 | specification URL + 문서 버전 |

핵심 URL은 다음과 같이 고정한다.

```text
https://github.com/openai/codex/blob/2cf2a6a844f1fc2ddd489c8a67fa8bc2f59a6f3d/codex-rs/protocol/src/prompts/base_instructions/default.md
https://code.claude.com/docs/en/headless#create-a-commit
https://code.claude.com/docs/en/configuration
https://code.claude.com/docs/en/permissions
https://code.claude.com/docs/en/hooks
https://www.conventionalcommits.org/en/v1.0.0/
```

현재 관찰 버전은 `codex-cli 0.146.0`, `Claude Code 2.1.220`이다. 버전·공식 문서
경로·changelog에서 `git`, `commit`, `attribution`, `permission`, `hook`,
`includeGitInstructions` 관련 변경이 관찰되면 자동 반입하지 않고 behavior contract
의미 검토 후보로 올린다. 네트워크/API 오류가 발생하면 마지막 accepted 관찰을 지우지
않고 `stale`로 표시한다.

registry schema는 `behavior_contracts`와 `target.behavior_contracts`를 지원하도록
v1.1로 확장한다. behavior-only source는 `target.local_skills`에 직접 매핑하지
않으며, contract가 `consumers.skills: ["commit"]`와 문서·검증 consumer를 가진다.
각 contract claim은 다음 class 중 하나를 가진다.

- `official-documented`: 공식 문서·공식 저장소가 직접 설명한 사실
- `local-policy`: 이 저장소가 안전·품질을 위해 추가한 규칙
- `runtime-observation`: 특정 CLI 버전과 fixture에서 관찰한 결과

필수 local policy는 명시적 커밋 요청 전 실행 금지, 의도한 범위만 stage, unrelated
변경 보존, staged diff 재검토, 기존 hook 정상 실행, `--no-verify`·amend·push·tag의
별도 요청 필요, commit 후 SHA/status/show 검증이다. 사용자 프로젝트의 실제 테스트
명령은 저장소별로 다르므로 commit 스킬이 임의의 전체 테스트나 pre-commit 정규식
스캐너를 강제하지 않는다.

Codex·Claude smoke는 같은 임시 fixture에서 status/diff/stage 경계·메시지·hook·사후
검증을 확인하되, 결과는 제품 간 동등성 선언이 아니라 `runtime-observation`으로만
기록한다. 공식 `commit` 스킬·plugin 파일을 복사하거나 특정 skill source를
upstream으로 삼지 않는다.

### 3.5 업스트림 거버넌스 문서 통합 기준선

현재 사람용 업스트림 거버넌스 계약은 다음 세 파일에 나뉘어 있다.

| 원본 | 현재 크기 | 고유 책임 |
|---|---:|---|
| `.user-docs/Skill_Upstream_Update_Policy.md` | 105줄 / 5,520바이트 | mode·상태·G0~G8·watched-path·보호 자산·책임·rollback 정책 |
| `.user-docs/Imported_Skill_Provenance.md` | 125줄 / 10,142바이트 | `adapted`·`vendored` 출처, 고정 ref, license/NOTICE/file-map, 변형·제외·패키징 상태 |
| `.user-docs/External_Skill_References.md` | 118줄 / 11,541바이트 | `reference` 출처, 소비자·참조 범위, 관찰값, 동작 동등성 한계·검증 절차 |

통합 정본은 `.user-docs/Skill_Upstream_Governance.md`로 한다. 통합은 세 파일을
그대로 이어 붙이는 작업이 아니라 **규범 의미를 보존하면서 중복을 제거하고 현행
machine-readable 사실로 갱신하는 작업**이다. 원문에 있던 오래된 사실도 버리지 않고
coverage manifest에서 `historical` 또는 `superseded`로 분류해 이유와 새 근거를 남긴다.

새 문서 제목과 짧은 목적 설명 바로 다음에는 반드시 다음 순서의 요약을 둔다.

1. `로컬 대상 ← 외부 출처`가 “왼쪽 로컬 대상이 오른쪽 외부 upstream을 반입·변형
   또는 참고한다”는 뜻임을 설명하는 읽기 규칙
2. **직접 반입·변형 관계 요약**: 누가 무엇의 upstream 반영인지 표시
3. **개념·행동 참조 관계 요약**: 누가 무엇을 참고하며 무엇을 반입하지 않는지 표시
4. machine-readable 정본과 사람용 문서의 우선순위

상단 두 요약표의 최소 열은 다음과 같다.

| 표 | 필수 열 |
|---|---|
| 직접 반입·변형 | 로컬 대상, 외부 upstream, source ID, mode/lifecycle, accepted ref·40자 SHA, 반영·변형 범위, 포함·제외 자산, 사용자 payload 포함 여부, license/NOTICE/file-map |
| 개념·행동 참조 | 로컬 소비자, 외부 출처, source/contract ID, 참조 목적, 반영된 행동·불변조건, 비반입 범위, observed ref·확인일·증적 상태, stale 처리 |

상단 요약 뒤의 본문은 다음 순서로 구성한다.

1. machine-readable 정본과 필드 우선순위
2. 출처 mode·lifecycle·evidence state 모델과 G0~G8
3. 직접 반입·변형 provenance와 패키징·라이선스 의무
4. 개념 reference와 스킬별 채택 범위
5. behavior contract와 claim class
6. 다중 upstream·`relationship_group` 규칙
7. observed/accepted 최신화·watched-path 실패·stale 처리
8. 동작 동등성·격리 fixture·정적/실행 증적 구분
9. 보호 자산·파괴적 변경 승인·관리자 책임 경계
10. 검증 명령·증적 위치·rollback
11. 구 세 문서의 migration·superseded 항목 appendix

상단 표는 `registry.json`의 활성 관계를 기준으로 생성·검토하고 다음 관계를 빠뜨리지
않는다.

- 직접 반입·변형: `humanize-korean ← im-not-ai`,
  `frontend-design ← Anthropic frontend-design`,
  `custom-skill-design ← Anthropic skill-creator`,
  `ui-ux-pro-max ← UI/UX Pro Max`, `motion-design ← LottieFiles Motion Design`
- 개념 참조: OpenAI Product Design, Superpowers, gstack, OpenAI Codex
  `skill-creator`, Conventional Commits, OpenAI `AGENTS.md`, Claude Code memory,
  UI/UX Pro Max principles, Motion Design principles와 각 로컬 소비자
- 행동 참조: OpenAI Codex·Anthropic Claude Code 공식 Git 동작 출처가
  `commit-workflow`를 거쳐 `commit` 소비자로 연결되는 관계. behavior-only source를
  직접 반입 또는 `commit`의 파일 upstream으로 표현하지 않는다.

본문에는 다음 의미 단위를 모두 보존한다.

| 출처 문서 | 누락 금지 내용 |
|---|---|
| 업데이트 정책 | `native/reference/vendored/adapted/unknown` 5개 mode, `observed/accepted/embedded/packaged/released` 5개 상태, G0~G8, exact watched-path 관찰 원자성, `relationship_group` 원자 승격, 보호 자산 전체 목록, 두 관리자 스킬의 책임 분리, rollback 필드·재검증 |
| 직접 반입 provenance | 4개 upstream 저장소와 5개 `adapted` 관계의 immutable ref·SHA·license·NOTICE·file-map·변형/제외 방식, active `vendored=0`, UI/UX·Motion의 이중 관계, Motion 제3자 인용 권리 경고, `custom-skill-design`의 Anthropic adapted + OpenAI reference 이중 upstream, 동작 검증 한계, 향후 직접 반입 필수 필드 |
| 외부 reference | 9개 reference source의 링크·분류·소비자·목적·추적 방식·확인일, impl 계열의 Superpowers/gstack 채택 범위, 관찰 snapshot과 rate-limit 한계, `observed ≠ accepted`, 관계별 동등성 기준, 격리 fixture 비교 절차, 관리자 명령, reclassification 정책, machine-readable 경로 |

세 문서의 통합 시점 현황은 반드시 machine-readable 정본과 대조한다.

- `registry.json`: 관계·policy·source ID 정본
- `lock.json`: observed·accepted·embedded·packaged·released 증적 정본
- `maintainer/plugin/CAPABILITIES.json`, `maintainer/plugin/release.json`: 사용자 skill 수와
  패키징·릴리스 상태 정본
- `maintainer/upstreams/provenance/**`: license, NOTICE, file-map 정본

따라서 현재 원문에 있는 UI/UX Pro Max·Motion Design의 “패키징 대기/예정”, 일부
NOTICE만 생성됐다는 표현, 모든 관계를 2026-07-30 하나의 관찰일로 묶은 표현은 그대로
현행화하지 않는다. Phase 1 완료 기준인 사용자 skill 19개와 source별 lock 관찰일,
UI/UX·Motion을 포함한 패키징 NOTICE 상태로 정정하되 원문 사실은 merge manifest에서
`superseded`로 추적한다. `pre-commit`의 과거 Superpowers 참조도 live 소비자에서는
제거하고 historical 항목으로 보존하며 `commit`에 자동 승계하지 않는다.

`maintainer/inventory/upstream-governance-doc-merge.json`은 최소한 다음 필드를 가진다.

```text
source_path
source_sha256
source_heading
source_row_or_rule_id
destination_path
destination_anchor
disposition = merged | deduplicated | historical | superseded
reason
evidence_source
```

세 원본의 모든 제목, 표 행, 목록 규칙, 명령 블록, 증적 경로는 정확히 한 항목 이상에
매핑되어야 한다. `deduplicated`는 새 문서의 하나의 공통 규칙으로 합쳐진 경우에만,
`historical`·`superseded`는 이유와 현행 정본을 기록한 경우에만 허용한다.

경로 변경 영향은 단순 Markdown 링크에 한정되지 않는다. 다음 live referrer를 같은
Phase에서 새 경로·anchor로 전환한다.

- `README.md`, `.user-docs/README.md`, `Harness_Engineering.md`,
  `Harness_Engineering_Intro.md`, `Agent_Skills_Repo_Structure_Analysis.md`
- `skills/frontend-design/**`, `skills/ui-ux-pro-max/SKILL.md`,
  `skills/motion-design/SKILL.md`
- `maintainer/skills/skill-portfolio-maintainer/scripts/validate_registry.py`와 해당 eval
- 현재 계획서의 live 경로와 기타 `rg`로 발견한 canonical source
- `.agents/skills/**`, `.claude/skills/**`, `plugins/**`는 직접 수정하지 않고 후속
  projection·plugin 재생성으로 전파

기존 세 파일은 새 문서와 coverage manifest, live referrer, validator가 먼저 통과한
후 같은 Phase의 마지막 파괴적 단계에서 제거한다. 한 줄 redirect stub도 별도 정본으로
오해될 수 있으므로 기본안에는 두지 않는다. 과거 `improvement_plan/**`의 경로 기록은
historical evidence로 보존하고, 새 문서의 migration appendix와 Git history를 복구
경로로 사용한다.

### 3.6 구현계획 roadmap index 선행 계약

현재 `impl-doc`·`impl-fe-be-doc`에는 계획서를 저장한 뒤 Step 8에서 roadmap index를
갱신하는 규칙이 있다. 이 계획에서는 그 사후 갱신을 폐기하지 않고, **계획서 작성 전
preflight와 계획서 저장 후 확정 갱신의 두 단계 계약**으로 확장한다.

1. 계획서 초안을 만들기 전에 다음 값을 먼저 확인한다.
   - 사용자 식별자와 계정 범위
   - 단일 앱인지 복수 앱인지, 앱 식별자와 각 앱 root
   - repository root, `.docs` root, `impl-doc` root
   - `../impl-doc/{사용자 식별}/` 아래의 `design-roadmap` 실제 위치와 접근 가능한
     기존 `*-roadmap-impl-index.md` 목록
2. 단일 앱은 `.docs/impl-doc/{사용자}/`, 복수 앱은
   `.docs/{앱}/impl-doc/{사용자}/`를 계획서·인덱스의 동일 scope로 사용한다. 경로가
   없거나 앱 식별자가 모호하면 파일을 쓰지 않고 사용자 확인을 요구한다.
3. 대상 scope에서 인덱스가 0개이면 계획서 저장 전에
   `{YYMMDD}-0.{앱이름}-roadmap-impl-index.md`를 만들고, 최소한 skill, 사용자,
   앱, 계획 slug/kind, `implementation plan pending` 예약 상태, preflight 시각,
   `design-roadmap` 경로를 기록한다. 이미 구현계획서가 있는데 인덱스가 없으면
   기존 계획서와 인덱스를 역추적해 backfill한다.
4. 인덱스가 2개 이상이면 이름순으로 임의 선택하지 않는다. 각 후보의 scope·hash·최근
   상태를 보고 사용자에게 정본을 선택받을 때까지 계획서 작성을 중단한다.
5. 계획서 저장 직후에는 같은 행을 `planned`·phase·파일 경로·계획서 SHA-256·현재
   roadmap 위치로 확정 갱신한다. 취소된 계획은 행을 지우지 않고 `cancelled`와 사유를
   남겨 재사용·추적 가능성을 유지한다.
6. 두 스킬은 하나의 공유 index 계약을 사용한다. `impl-fe-be-doc`이 별도 인덱스를
   만들거나 `impl-doc`의 행을 복제하지 않는다. index는 계획서 bundle/fingerprint에
   포함하고, `impl-reuse-scan`·`impl-verify`는 검증된 index가 연결된 계획서만 정상
   입력으로 인정한다.

### 3.7 사용자 산출물 위치와 공용 `@instruction` 기준선

산출물 생성 스킬의 파일 쓰기는 스킬별 관행이 아니라 하나의 공용 instruction을
따른다. 새 instruction의 정본 이름과 연결 위치는 다음과 같다.

- 단일 앱: `.docs/instruction/artifact-output-routing-instruction.md`
- 복수 앱: `.docs/{앱}/instruction/artifact-output-routing-instruction.md`
- 단일 앱 `AGENTS.md`는 `@.docs/instruction/artifact-output-routing-instruction.md`를
  직접 참조한다. 복수 앱은 각 `.docs/{앱}-context.md`와
  `.docs/root-context/AGENTS.md`가 해당 앱 instruction을 index하고, root
  `AGENTS.md`·`CLAUDE.md`는 bridge만 유지한다.

계약 매니페스트는 `maintainer/inventory/artifact-output-contract.json`에 두며 최소
필드는 `skill`, `scope`, `artifact_class`, `persistence`, `single_app_path`,
`multi_app_path`, `owner`, `approval`, `handoff`, `evidence`이다. `scope`는
`user` 또는 `manager`, `artifact_class`는 다음 다섯 값 중 하나로 제한한다.

| 산출물 클래스 | 대상 스킬 | 단일 앱 기본 위치 | 복수 앱 기본 위치 | 쓰기·인계 규칙 |
|---|---|---|---|---|
| managed-project-output | `design-doc` | `.docs/context-base/DESIGN.md` | `.docs/{앱}/context-base/DESIGN.md` | 승인된 설계 정본, context 계열이 참조 |
| managed-project-output | `context-doc`, `harness-bootstrap`, `harness-setup` | root `AGENTS.md`·`CLAUDE.md` 및 `.docs/instruction/*` | `.docs/{앱}-context.md`, `.docs/{앱}/instruction/*`, `.docs/root-context/*`, root bridge | instruction과 context index를 함께 갱신 |
| managed-project-output | `impl-doc`, `impl-fe-be-doc` | `.docs/impl-doc/{사용자}/...` | `.docs/{앱}/impl-doc/{사용자}/...` | roadmap index preflight·post-save를 필수화 |
| managed-project-output | `design-prototype-docs`, `create-prototype` | `.docs/prototype/{사용자}/{식별자}/...` | `.docs/{앱}/prototype/{사용자}/{식별자}/...` | display/data/css/script/docs bundle 소유권 유지 |
| managed-project-output | `ui-ux-pro-max`, `motion-design` | `.docs/design-system/{project-slug}/...` | `.docs/{앱}/design-system/{project-slug}/...` | 명시적 저장 승인 후 master/page/motion 생성 |
| source-mutation | `frontend-design`, `code-comment`, `humanize-korean` | 사용자 지정 source root 또는 입력 artifact 원위치 | 앱 source root 또는 해당 입력 artifact 원위치 | `.docs`에 제품 source를 복제하지 않음; outer producer owner 보존 |
| source-mutation | `commit` | repository `.git` history | 각 앱 repository의 `.git` history | 파일 산출물 경로가 아니라 명시적 사용자 요청에 따른 Git 상태 변경; commit evidence를 handoff |
| source-mutation | `git-scoped-account` | 사용자가 지정한 project container의 shared gitconfig | 앱별 사용자가 지정한 project container의 shared gitconfig | 명시적 요청 없이는 생성하지 않으며 계정·secret을 `.docs`에 기록하지 않음 |
| report-only / chat-only | `impl-reuse-scan`, `impl-verify`, `doc-audit`, `multi-review` | 기본 파일 미생성, chat report | 기본 파일 미생성, chat report | 명시적 저장 요청 없이는 임의 Markdown 생성 금지 |
| manager-repository-output | `custom-skill-design`, `harness-plugin-maintainer`, `skill-portfolio-maintainer` | manager repo의 `maintainer/**` | manager repo의 `maintainer/**` | 사용자 `.docs`와 교차 쓰기 금지 |

현재 `design-prototype-docs`, `create-prototype`, `ui-ux-pro-max`, `motion-design`의
복수 앱 공통 경로는 앱 prefix가 없는 충돌 위험 상태로 분류한다. Phase 3에서 기존
파일을 조용히 이동하지 않고, 앱 식별자·migration map·사용자 승인·SHA-256·link
검증을 거쳐 `.docs/{앱}/...`로 정규화한다. `frontend-design`은 실제 애플리케이션
source를 산출하므로 `.docs` artifact로 분류하지 않으며, 앱 source root 계약만
instruction에 연결한다.

매니페스트는 위 19개 사용자 스킬과 3개 관리자 스킬을 정확히 한 번씩 포함해야 한다.
분류되지 않은 쓰기 가능 스킬, 단일/복수 경로가 같은데 scope가 다른 스킬, owner와
handoff가 없는 항목은 validator 실패로 처리한다. 새
`validate_artifact_output_contract.py`는 매니페스트·SKILL.md·생성 template·AGENTS/
CLAUDE의 `@` 참조를 1:1 대조하고, 앱 A의 산출물이 앱 B 또는 manager repo에 쓰이는
경로를 거부한다.

탐지는 수기 목록에 의존하지 않는다. `skills/*/SKILL.md`와
`maintainer/skills/*/SKILL.md`를 `rg --files`로 전수 열거하고, registry의 active
target과 대조한 뒤 `write`, `save`, `create`, `update`, `commit`, `generate` 및
경로 패턴(`.docs/`, `AGENTS.md`, `CLAUDE.md`, `source root`, `.git`)을 검사한다.
검출된 모든 스킬은 파일을 만들지 않는 경우에도 `chat-only`·`report-only`로 명시해
매니페스트에 넣는다. 새 스킬이 추가되면 매니페스트와 instruction을 먼저 갱신하지
않는 한 build/eval을 통과할 수 없게 한다.

### 3.8 impl 계획 산출물의 reuse·verify downstream 계약

현재 정적 상태는 부분적으로만 연결되어 있다. `impl-doc` 흐름도에는 두 downstream
스킬이 있지만 `impl-fe-be-doc` 흐름도에는 roadmap만 있고, `harness-bootstrap`은
두 스킬을 `(선택)`으로 표현한다. 또한 `impl-verify`는 안전 경계를 위해 명시 호출
전용이므로, 모델이 계획 생성 중에 검증 명령을 자동 실행하도록 연결해서는 안 된다.
이 계획에서는 다음을 정본 계약으로 삼는다.

1. **계획 승인·index 확정**: `impl-doc` 또는 `impl-fe-be-doc`이 계획서와 roadmap
   index의 preflight·저장·hash 검증을 끝낸다. 이 단계에서는 구현·reuse scan·verify
   명령을 실행하지 않는다.
2. **Phase/태스크 시작 전 `impl-reuse-scan`**: 계획서의 해당 Phase/태스크 경로,
   앱 source root, roadmap index, 생성 예정 자산 목록을 입력으로 명시 호출한다.
   보고서만 산출하며 자동 코드·계획서 패치는 하지 않는다. 공통 자산이 없거나 해당
   작업이 순수 설정·문서인 경우에도 `not-applicable`과 사유를 기록한 뒤 구현을
   시작한다. 후보가 있으면 사용자 결정(재사용/확장/신규/보류)이 먼저 완료되어야
   한다.
3. **실제 구현**: reuse 결정과 계획서 범위가 일치하는지 확인한 뒤 한 Phase 또는
   한 태스크만 수행한다. reuse 결과를 계획서에 자동 주입하지 않고, 승인된 결정의
   evidence reference만 index/hand-off 기록에 연결한다.
4. **Phase/태스크 종료 `impl-verify`**: 계획서 경로, `task`·`phase`·`full` 범위,
   구현 산출물 root를 함께 명시해 사용자가 직접 호출한다. Codex 공개 호출은
   `$impl-verify`, Claude 공개 호출은 새 plugin namespace 기준
   `/harness-kit:impl-verify`로 기록한다. 검증은 PASS/FAIL/SKIP 리포트만 만들고
   코드·계획서·구현 결과를 자동 수정하지 않는다. FAIL은 다음 Phase 진입 불가
   권고로 index/hand-off에 전달한다.
5. `impl-verify`의 `disable-model-invocation: true`와 plugin validator의
   `EXPLICIT_ONLY_SKILLS` 등록은 유지한다. 계획서에 route가 있다고 해서 자동
   하위 skill 호출로 해석하지 않으며, 명시 호출이 없으면 `verify=pending`으로
   남긴다. `impl-reuse-scan`은 자동 패치를 하지 않는 preflight이지만, 계획서가
   생성한 입력·범위가 없으면 호출하지 않고 `handoff=blocked`로 보고한다.
6. 두 계획 스킬은 동일한 downstream 블록을 산출한다. 최소 필드는 다음과 같다.

   ```yaml
   downstream:
     roadmap_index: <verified index path>
     phase: <phase id>
     reuse_scan:
       skill: impl-reuse-scan
       trigger: phase-start
       status: required | not-applicable | passed | pending
       input: <plan path + task/asset scope + source root>
       decision: reuse | extend | new | deferred | pending
       evidence: <report reference or reason>
     verify:
       skill: impl-verify
       trigger: phase-end
       invocation: explicit-only
       status: required | passed | failed | skipped | pending
       input: <plan path + task/phase/full scope + implementation root>
       evidence: <verification report reference>
   ```

   이 블록은 계획서와 index의 동일 Phase 행에 연결한다. report-only 스킬이 기본적으로
   파일을 만들지 않으므로 evidence는 대화 결과·사용자 지정 report 경로·hash 중 하나로
   명시하며, 근거 없는 `passed`를 허용하지 않는다.
7. `impl-fe-be-doc`의 스킬 연계도 `impl-doc`과 동일하게
   `impl-reuse-scan → 구현 → impl-verify → multi-review/doc-audit`를 표시한다.
   `harness-bootstrap`·`design-doc`·README는 구현을 시작하는 정상 경로에서 reuse를
   선택사항으로 표현하지 않고, “재사용 불가 판정도 포함한 필수 preflight”로 설명한다.

## 5. 전역 안전 규칙

- root `example/` 삭제는 사용자의 명시적 승인과 삭제 전 inventory 보존 후에만
  수행한다. 이번 실행은 그 승인을 받았으므로 정확한 root만 제거한다.
- `skills/**/example(s)`는 plugin payload 보호 자산이므로 root 삭제와 함께
  `Remove-Item`, `git rm`, 이동하지 않는다.
- `0.2.2` archive와 `v0.2.2` tag는 immutable 기준선으로 취급한다.
- `ai-agent-harness` 문자열을 전역 치환하지 않는다. repository URL,
  historical plan, old archive, migration note인지 live plugin identity인지 파일별로
  분류한다.
- `AGENTS.md`와 `.user-docs/**`가 root 제거와 내부 보호 경계를 설명하고, local-link
  검사가 통과하기 전에는 Phase 2를 완료로 표시하지 않는다.
- `origin` URL은 `https://hb9397@github.com/hb9397/harness-kit.git`로 확인할 수
  있지만 token을 URL에 저장하지 않는다. `user.name`·`user.email`은 commit identity와
  push authentication을 혼동하지 않도록 별도로 점검한다.
- `core.worktree`·hook·include 설정이 새 checkout을 절대 경로로 묶고 있지 않은지
  확인한다.
- `commit-workflow`의 official-documented, local-policy, runtime-observation을
  섞어 제품 보장처럼 기록하지 않는다. 공식 문서에 없는 자동 stage·테스트·사후
  검증 알고리즘은 local policy로만 선언한다.
- 세 upstream 문서는 파일 수를 줄이기 전에 SHA-256·제목·표 행·규범·명령·증적
  경로를 coverage manifest로 고정한다. `누락 없음`은 단순 문자열 복사가 아니라
  각 의미 단위가 새 anchor 또는 근거 있는 historical/superseded 처리로 추적되는
  상태를 뜻한다.
- 새 통합 문서·referrer·validator가 모두 통과하기 전에는 기존 세 문서를 삭제하지
  않는다. machine-readable 정본과 충돌하는 오래된 현황은 live 사실로 복사하지 않고
  superseded 사유와 정본 경로를 기록한다.
- `integration_mode`, registry `lifecycle`, lock evidence state는 서로 다른 축이다.
  통합 문서에서 하나의 status로 합치지 않는다.
- Phase 1의 source/registry 변경으로 기존 `0.2.2` generated tree에 drift가 생길 수
  있음을 기록한다. Phase 1에서 release-ready나 full build-green을 주장하지 않고,
  identity 재생성 Phase의 targeted gate로 회복을 확인한다.
- 생성물은 `sync_manager_projections.py`, `build_plugin.py`, 검증기에서만 갱신한다.
- 각 Phase는 구현·검증·커밋을 한 묶음으로 완료한다. push·tag·release는 마지막
  별도 승인 전까지 수행하지 않는다.

## 6. 구현 Phase

### Phase 0 — 기준선·inventory·변경 허용 목록 고정

**목표**: `0.2.2`, plugin identity, root `example/` 보호 자산, 현재 live reference를
수치와 hash로 고정한다.

작업:

1. `git status --short --branch`, `git rev-parse HEAD`, `git show-ref --tags v0.2.2`로
   작업 트리와 tag를 기록한다.
2. `git remote -v`, `git config --local --get-regexp '^(remote\\.|branch\\.|core\\.|include\\.)'`,
   `git rev-parse --show-toplevel`로 새 checkout·remote·tracking을 기록한다.
3. `git ls-files example`와 파일별 SHA-256을 기록한다.
4. `maintainer/inventory/example-externalization-baseline.json`을 새로 만들고
   파일 목록·바이트 수·SHA-256·기준 commit을 기록한다.
5. `ai-agent-harness` hit를 live identity, repository URL, historical record,
   old release artifact, migration note로 분류한다.
6. `.docs/**`와 skill-internal `example(s)`가 변경 대상에서 제외되었는지 확인한다.

검증:

```powershell
git status --short --branch
git rev-parse HEAD
git show-ref --tags v0.2.2
git remote -v
git rev-parse --show-toplevel
git ls-files example
Get-ChildItem -LiteralPath 'example' -Recurse -File |
  Get-FileHash -Algorithm SHA256
git diff --check
git diff --cached --check
```

완료 기준: clean worktree, `origin`이 새 repository URL을 가리킴, Phase 2 source
snapshot 기준 root example 11개/225,213바이트, 기존 pre-Phase 1 snapshot
225,227바이트는 `previous_snapshot`으로 보존, 기존 archive hash 일치, baseline JSON
검토 완료.

### Phase 1 — 사용자 스킬 포트폴리오 정비와 `commit-workflow` 채택

| `.docs` 계약 변경 | `git diff -- .docs` 또는 관련 template diff | 해당 변경 즉시 제거; 사용자 산출 경로는 범위 밖 |
| Desktop/model 증적 부재 | release gate `not-release-ready` | 기술 검증과 readiness를 분리해 상태 유지 |

rollback은 `v0.2.2` tag와 보존 archive를 기준으로 한다. 새 `0.3.0` artifact를
삭제하거나 old tag를 force-update하지 않는다. root `example/` 삭제 후 정책·검증이
실패하면 해당 Phase 커밋을 revert하거나 `v0.2.2`에서 root 파일을 복원하고, 내부
skill examples는 별도 복구 검증을 거친다.
