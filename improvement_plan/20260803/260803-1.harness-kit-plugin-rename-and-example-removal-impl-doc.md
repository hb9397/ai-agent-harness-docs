## 1. 목적과 결정 사항

이 계획은 선행 사용자 스킬 정비와 두 개의 후속 파괴적 변경을 안전하게 수행하기
위한 작업 지침이다.

1. `pre-commit` 스킬을 제거하고 `commit` 스킬을 Codex·Claude의 명시적 Git 커밋
   행동 계약에 맞게 강화한다.
2. `.user-docs/Skill_Upstream_Update_Policy.md`,
   `.user-docs/Imported_Skill_Provenance.md`,
   `.user-docs/External_Skill_References.md`의 규범·현황·증적을 누락 없이
   `.user-docs/Skill_Upstream_Governance.md` 하나로 통합한다.
3. 현재 `ai-agent-harness` 플러그인의 설치 정체성을 `harness-kit`으로 변경한다.
4. marketplace 식별자를 `ai-agent-harness`에서 `hb9397`로 변경한다.
5. Git remote와 plugin provenance의 repository URL을 `hb9397/harness-kit`으로 정합화한다.
6. 새 로컬 checkout 기준 경로 `C:/Plugin_Workspace/harness-kit`을 사용하고
   machine-specific 절대 경로를 생성 metadata에서 제거한다.
7. 루트 보호 자산 `example/`을 외부 examples 저장소로 이관한 뒤 현재 저장소에서 제거한다.

### 1.1 이름 선정 이유

`harness-kit`을 선택한다. 짧고 kebab-case 검증 규칙에 맞으며, 선행 `pre-commit`
제거 후 19개 사용자
스킬이 제공하는 설계·구현·검증·문서화 흐름을 특정 모델이나 한 가지 산출물에
가두지 않는다.

| 후보 | 판단 |
|---|---|
| `harness-kit` | **선정**. 범용적이고 설치 표면이 짧으며 확장 가능 |
| `project-harness` | 의미는 명확하지만 일반 명사 조합이라 브랜드 식별성이 약함 |
| `workflow-harness` | workflow에 치우쳐 문서·품질·스킬 포트폴리오를 충분히 표현하지 못함 |
| `agent-workbench` | IDE·실험 도구로 오해할 가능성이 있음 |

### 1.2 호환성 정책

plugin ID와 qualified install 문자열은 사용자 설치 계약이므로 이번 변경은 공개
설치 표면의 breaking change다. `0.2.2`의 manifest, archive, tag를 덮어쓰지 않고
`0.3.0`으로 승격한다. 기본 정책은 별도 legacy alias를 만들지 않는 hard cutover다.

기존 사용자는 다음 순서로 이동한다.

```text
기존 ai-agent-harness@ai-agent-harness 제거
→ marketplace hb9397 갱신
→ harness-kit@hb9397 설치
→ 새 세션에서 skill 호출 확인
```

legacy alias를 병행하면 두 plugin ID와 두 cache 경로를 계속 검증해야 하므로 이번
계획에는 포함하지 않는다. alias가 필요해지면 별도 호환성 계획으로 분리한다.

| 계층 | 현재 위치/값 | 목표 조치 |

```text

```

현재 checkout 이동은 `.git/config`에 `core.worktree`가 없으므로 Git object와

### 3.4 `commit-workflow` 행동 기준과 upstream/reference 정책

`commit`을 특정 외부 스킬의 복제본으로 관리하지 않는다. Codex·Claude의 공식 Git
동작에서 확인되는 공통 행동과 이 저장소의 명시적 local policy를
`commit-workflow`라는 behavior contract로 관리한다. 공식 제품이 공개하지 않은
세부 알고리즘은 제품 보장으로 표현하지 않고 `local-policy` 또는
`runtime-observation`으로 분리한다.

공식 관찰 출처는 다음과 같다.

| source id | 공식 기준 | 추적 방식 |
|---|---|---|
| `openai-codex-commit-behavior` | Codex 기본 지침·AGENTS.md·approval/sandbox·review·customization 문서 | 문서 URL + watched path commit SHA + 관찰한 `codex-cli` 버전 |
| `anthropic-claude-code-commit-behavior` | Claude Code headless commit 예시·built-in Git instructions·permission·hooks·attribution·changelog | 문서 URL + checked_at + 정규화 content hash + 관찰한 Claude Code 버전 |
| `conventional-commits` | Conventional Commits 1.0.0 메시지 문법 | specification URL + 문서 버전 |

핵심 URL은 다음과 같이 고정한다.

```text
https://github.com/openai/codex/blob/2cf2a6a844f1fc2ddd489c8a67fa8bc2f59a6f3d/codex-rs/protocol/src/prompts/base_instructions/default.md
https://code.claude.com/docs/en/headless#create-a-commit
https://code.claude.com/docs/en/configuration
https://code.claude.com/docs/en/permissions
https://code.claude.com/docs/en/hooks
https://www.conventionalcommits.org/en/v1.0.0/
```

현재 관찰 버전은 `codex-cli 0.146.0`, `Claude Code 2.1.220`이다. 버전·공식 문서
경로·changelog에서 `git`, `commit`, `attribution`, `permission`, `hook`,
`includeGitInstructions` 관련 변경이 관찰되면 자동 반입하지 않고 behavior contract
의미 검토 후보로 올린다. 네트워크/API 오류가 발생하면 마지막 accepted 관찰을 지우지
않고 `stale`로 표시한다.

registry schema는 `behavior_contracts`와 `target.behavior_contracts`를 지원하도록
v1.1로 확장한다. behavior-only source는 `target.local_skills`에 직접 매핑하지
않으며, contract가 `consumers.skills: ["commit"]`와 문서·검증 consumer를 가진다.
각 contract claim은 다음 class 중 하나를 가진다.

- `official-documented`: 공식 문서·공식 저장소가 직접 설명한 사실
- `local-policy`: 이 저장소가 안전·품질을 위해 추가한 규칙
- `runtime-observation`: 특정 CLI 버전과 fixture에서 관찰한 결과

필수 local policy는 명시적 커밋 요청 전 실행 금지, 의도한 범위만 stage, unrelated
변경 보존, staged diff 재검토, 기존 hook 정상 실행, `--no-verify`·amend·push·tag의
별도 요청 필요, commit 후 SHA/status/show 검증이다. 사용자 프로젝트의 실제 테스트
명령은 저장소별로 다르므로 commit 스킬이 임의의 전체 테스트나 pre-commit 정규식
스캐너를 강제하지 않는다.

Codex·Claude smoke는 같은 임시 fixture에서 status/diff/stage 경계·메시지·hook·사후
검증을 확인하되, 결과는 제품 간 동등성 선언이 아니라 `runtime-observation`으로만
기록한다. 공식 `commit` 스킬·plugin 파일을 복사하거나 특정 skill source를
upstream으로 삼지 않는다.

### 3.5 기존 식별자 잔존 범위와 파일 분류

구현 전에 다음 패턴을 저장소 전체에서 검색하고, 각 hit를 `live`, `generated`,
`test-fixture`, `historical`로 분류한다. `ai-agent-harness`를 단순 전역 치환하지
않으며, live 항목은 새 정본으로 갱신하고 generated 항목은 generator로 재생성한다.

### 3.6 업스트림 거버넌스 문서 통합 기준선

현재 사람용 업스트림 거버넌스 계약은 다음 세 파일에 나뉘어 있다.

| 원본 | 현재 크기 | 고유 책임 |
|---|---:|---|
| `.user-docs/Skill_Upstream_Update_Policy.md` | 105줄 / 5,520바이트 | mode·상태·G0~G8·watched-path·보호 자산·책임·rollback 정책 |
| `.user-docs/Imported_Skill_Provenance.md` | 125줄 / 10,142바이트 | `adapted`·`vendored` 출처, 고정 ref, license/NOTICE/file-map, 변형·제외·패키징 상태 |
| `.user-docs/External_Skill_References.md` | 118줄 / 11,541바이트 | `reference` 출처, 소비자·참조 범위, 관찰값, 동작 동등성 한계·검증 절차 |

통합 정본은 `.user-docs/Skill_Upstream_Governance.md`로 한다. 통합은 세 파일을
그대로 이어 붙이는 작업이 아니라 **규범 의미를 보존하면서 중복을 제거하고 현행
machine-readable 사실로 갱신하는 작업**이다. 원문에 있던 오래된 사실도 버리지 않고
coverage manifest에서 `historical` 또는 `superseded`로 분류해 이유와 새 근거를 남긴다.

새 문서 제목과 짧은 목적 설명 바로 다음에는 반드시 다음 순서의 요약을 둔다.

1. `로컬 대상 ← 외부 출처`가 “왼쪽 로컬 대상이 오른쪽 외부 upstream을 반입·변형
   또는 참고한다”는 뜻임을 설명하는 읽기 규칙
2. **직접 반입·변형 관계 요약**: 누가 무엇의 upstream 반영인지 표시
3. **개념·행동 참조 관계 요약**: 누가 무엇을 참고하며 무엇을 반입하지 않는지 표시
4. machine-readable 정본과 사람용 문서의 우선순위

상단 두 요약표의 최소 열은 다음과 같다.

| 표 | 필수 열 |
|---|---|
| 직접 반입·변형 | 로컬 대상, 외부 upstream, source ID, mode/lifecycle, accepted ref·40자 SHA, 반영·변형 범위, 포함·제외 자산, 사용자 payload 포함 여부, license/NOTICE/file-map |
| 개념·행동 참조 | 로컬 소비자, 외부 출처, source/contract ID, 참조 목적, 반영된 행동·불변조건, 비반입 범위, observed ref·확인일·증적 상태, stale 처리 |

상단 요약 뒤의 본문은 다음 순서로 구성한다.

1. machine-readable 정본과 필드 우선순위
2. 출처 mode·lifecycle·evidence state 모델과 G0~G8
3. 직접 반입·변형 provenance와 패키징·라이선스 의무
4. 개념 reference와 스킬별 채택 범위
5. behavior contract와 claim class
6. 다중 upstream·`relationship_group` 규칙
7. observed/accepted 최신화·watched-path 실패·stale 처리
8. 동작 동등성·격리 fixture·정적/실행 증적 구분
9. 보호 자산·파괴적 변경 승인·관리자 책임 경계
10. 검증 명령·증적 위치·rollback
11. 구 세 문서의 migration·superseded 항목 appendix

상단 표는 `registry.json`의 활성 관계를 기준으로 생성·검토하고 다음 관계를 빠뜨리지
않는다.

- 직접 반입·변형: `humanize-korean ← im-not-ai`,
  `frontend-design ← Anthropic frontend-design`,
  `custom-skill-design ← Anthropic skill-creator`,
  `ui-ux-pro-max ← UI/UX Pro Max`, `motion-design ← LottieFiles Motion Design`
- 개념 참조: OpenAI Product Design, Superpowers, gstack, OpenAI Codex
  `skill-creator`, Conventional Commits, OpenAI `AGENTS.md`, Claude Code memory,
  UI/UX Pro Max principles, Motion Design principles와 각 로컬 소비자
- 행동 참조: OpenAI Codex·Anthropic Claude Code 공식 Git 동작 출처가
  `commit-workflow`를 거쳐 `commit` 소비자로 연결되는 관계. behavior-only source를
  직접 반입 또는 `commit`의 파일 upstream으로 표현하지 않는다.

본문에는 다음 의미 단위를 모두 보존한다.

| 출처 문서 | 누락 금지 내용 |
|---|---|

세 문서의 통합 시점 현황은 반드시 machine-readable 정본과 대조한다.

NOTICE만 생성됐다는 표현, 모든 관계를 2026-07-30 하나의 관찰일로 묶은 표현은 그대로

`maintainer/inventory/upstream-governance-doc-merge.json`은 최소한 다음 필드를 가진다.

```text
source_path
source_sha256
source_heading
source_row_or_rule_id
destination_path
destination_anchor
disposition = merged | deduplicated | historical | superseded
reason
evidence_source
```

세 원본의 모든 제목, 표 행, 목록 규칙, 명령 블록, 증적 경로는 정확히 한 항목 이상에
매핑되어야 한다. `deduplicated`는 새 문서의 하나의 공통 규칙으로 합쳐진 경우에만,
`historical`·`superseded`는 이유와 현행 정본을 기록한 경우에만 허용한다.

경로 변경 영향은 단순 Markdown 링크에 한정되지 않는다. 다음 live referrer를 같은
Phase에서 새 경로·anchor로 전환한다.

- `README.md`, `.user-docs/README.md`, `Harness_Engineering.md`,

- `skills/frontend-design/**`, `skills/ui-ux-pro-max/SKILL.md`,
  `skills/motion-design/SKILL.md`
- `maintainer/skills/skill-portfolio-maintainer/scripts/validate_registry.py`와 해당 eval
- 현재 계획서의 live 경로와 기타 `rg`로 발견한 canonical source
- `.agents/skills/**`, `.claude/skills/**`, `plugins/**`는 직접 수정하지 않고 후속

기존 세 파일은 새 문서와 coverage manifest, live referrer, validator가 먼저 통과한
후 같은 Phase의 마지막 파괴적 단계에서 제거한다. 한 줄 redirect stub도 별도 정본으로

historical evidence로 보존하고, 새 문서의 migration appendix와 Git history를 복구

## 5. 전역 안전 규칙

- 이 문서 작성 시점에는 이름 변경과 root `example/` 삭제를 수행하지 않는다.
- `example/`은 보호 자산이므로 외부 clone 검증과 별도 파괴적 변경 승인 전에는
  `Remove-Item`, `git rm`, 이동을 실행하지 않는다.
- `0.2.2` archive와 `v0.2.2` tag는 immutable 기준선으로 취급한다.
- `ai-agent-harness` 문자열을 전역 치환하지 않는다. repository URL,
  historical plan, old archive, migration note인지 live plugin identity인지 파일별로
  분류한다.
- `AGENTS.md`와 `.user-docs/**`가 새 경로·설치명을 설명하기 전에는 root 제거를
  완료로 표시하지 않는다.
- `origin` URL은 `https://hb9397@github.com/hb9397/harness-kit.git`로 확인할 수
  있지만 token을 URL에 저장하지 않는다. `user.name`·`user.email`은 commit identity와
  push authentication을 혼동하지 않도록 별도로 점검한다.
- `core.worktree`·hook·include 설정이 새 checkout을 절대 경로로 묶고 있지 않은지
  확인한다.
- `commit-workflow`의 official-documented, local-policy, runtime-observation을
  섞어 제품 보장처럼 기록하지 않는다. 공식 문서에 없는 자동 stage·테스트·사후
  검증 알고리즘은 local policy로만 선언한다.
- 세 upstream 문서는 파일 수를 줄이기 전에 SHA-256·제목·표 행·규범·명령·증적
  경로를 coverage manifest로 고정한다. `누락 없음`은 단순 문자열 복사가 아니라
  각 의미 단위가 새 anchor 또는 근거 있는 historical/superseded 처리로 추적되는
  상태를 뜻한다.
- 새 통합 문서·referrer·validator가 모두 통과하기 전에는 기존 세 문서를 삭제하지
  않는다. machine-readable 정본과 충돌하는 오래된 현황은 live 사실로 복사하지 않고
  superseded 사유와 정본 경로를 기록한다.
- `integration_mode`, registry `lifecycle`, lock evidence state는 서로 다른 축이다.
  통합 문서에서 하나의 status로 합치지 않는다.
- Phase 1의 source/registry 변경으로 기존 `0.2.2` generated tree에 drift가 생길 수
  있음을 기록한다. Phase 1에서 release-ready나 full build-green을 주장하지 않고,
  identity 재생성 Phase의 targeted gate로 회복을 확인한다.
- 생성물은 `sync_manager_projections.py`, `build_plugin.py`, 검증기에서만 갱신한다.
- 각 Phase는 구현·검증·커밋을 한 묶음으로 완료한다. push·tag·release는 마지막
  별도 승인 전까지 수행하지 않는다.

## 6. 구현 Phase

### Phase 0 — 기준선·inventory·변경 허용 목록 고정

**목표**: `0.2.2`, plugin identity, root `example/` 보호 자산, 현재 live reference를
수치와 hash로 고정한다.

작업:

1. `git status --short --branch`, `git rev-parse HEAD`, `git show-ref --tags v0.2.2`로
   작업 트리와 tag를 기록한다.
2. `git remote -v`, `git config --local --get-regexp '^(remote\\.|branch\\.|core\\.|include\\.)'`,
   `git rev-parse --show-toplevel`로 새 checkout·remote·tracking을 기록한다.
3. `git ls-files example`와 파일별 SHA-256을 기록한다.
4. `maintainer/inventory/example-externalization-baseline.json`을 새로 만들고
   파일 목록·바이트 수·SHA-256·기준 commit을 기록한다.
5. `ai-agent-harness` hit를 live identity, repository URL, historical record,
   old release artifact, migration note로 분류한다.
6. `.docs/**`와 skill-internal `example(s)`가 변경 대상에서 제외되었는지 확인한다.

## 7. 위험·rollback

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| 외부 examples 이관 불완전 | clone hash mismatch | root 삭제 중단, 외부 commit 보완 |
| remote 설정 잔존 | `origin`이 old repository URL을 반환 | push 전 `git remote set-url origin`과 fetch 검증 |
| machine-specific path 잔존 | 다른 checkout에서 generated drift 또는 provenance mismatch | stable URL/relative marker로 정규화 |
| old plugin ID 잔존 | live docs/evidence에 old qualified ID 발견 | old hit 분류 후 live 파일만 정정 |
| generated path drift | build `--check` diff | source constant 수정 후 projection/plugin 재생성 |
| upstream 문서 의미 누락 | 원본 제목·표 행·규범에 destination anchor가 없음 | 원본 삭제 중단, merge manifest 미매핑 항목 보강 |
| stale 현황의 현행 오인 | UI/UX·Motion이 패키징 대기 또는 skill 20으로 표시 | registry·lock·CAPABILITIES·release 우선순위로 정정하고 원문은 superseded 처리 |
| direct/reference 관계 혼합 | adapted 자산이 reference로 표시되거나 behavior source가 skill source에 직접 연결 | 관계별 상단 표 분리, registry-driven semantic validator로 차단 |
| 구 문서 경로 결합 잔존 | validator·skill eval·Markdown link가 제거된 파일을 요구 | canonical source를 먼저 전환하고 projection/plugin 재생성 후 old-hit·link 검사 |
| 기존 사용자 cache 충돌 | old/new plugin이 동시에 목록에 노출 | migration 문서와 remove→install 순서 검증 |
| 내부 skill example 손실 | plugin manifest에서 internal path 누락 | root example 삭제를 되돌리고 builder 입력 확인 |
| `.docs` 계약 변경 | `git diff -- .docs` 또는 관련 template diff | 해당 변경 즉시 제거; 사용자 산출 경로는 범위 밖 |
| Desktop/model 증적 부재 | release gate `not-release-ready` | 기술 검증과 readiness를 분리해 상태 유지 |

rollback은 `v0.2.2` tag와 보존 archive를 기준으로 한다. 새 `0.3.0` artifact를
삭제하거나 old tag를 force-update하지 않는다. 외부 examples 저장소 이관이 실패하면
root `example/`은 원래 위치에 남긴다.
