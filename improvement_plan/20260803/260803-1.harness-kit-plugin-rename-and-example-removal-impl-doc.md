## 1. 목적과 결정 사항

이 계획은 두 개의 독립적인 파괴적 변경을 안전하게 수행하기 위한 작업 지침이다.

1. 현재 `ai-agent-harness` 플러그인의 설치 정체성을 `harness-kit`으로 변경한다.
2. marketplace 식별자를 `ai-agent-harness`에서 `hb9397`로 변경한다.
3. 루트 보호 자산 `example/`을 외부 examples 저장소로 이관한 뒤 현재 저장소에서 제거한다.

최종 설치 표면은 다음과 같다.

| 표면 | 현재 | 목표 | 비고 |
|---|---|---|---|
| plugin ID/name | `ai-agent-harness` | `harness-kit` | Codex·Claude manifest 공통 |
| marketplace name | `ai-agent-harness` | `hb9397` | 소유자 namespace와 일치 |
| qualified install | `ai-agent-harness@ai-agent-harness` | `harness-kit@hb9397` | 새 설치·업데이트 기준 |
| display name | `AI Agent Harness` | `Harness Kit` | 사용자에게 보이는 이름 |
| plugin root | `plugins/ai-agent-harness/` | `plugins/harness-kit/` | builder 파생 경로 |
| archive | `ai-agent-harness-0.2.2.zip` | `harness-kit-0.3.0.zip` | 기존 archive 불변 보존 |
| repository URL | `hb9397/ai-agent-harness-docs` | 유지 | 저장소 URL 변경은 별도 범위 |

### 1.1 이름 선정 이유

`harness-kit`을 선택한다. 짧고 kebab-case 검증 규칙에 맞으며, 현재 20개 사용자
스킬이 제공하는 설계·구현·검증·문서화 흐름을 특정 모델이나 한 가지 산출물에
가두지 않는다.

| 후보 | 판단 |
|---|---|
| `harness-kit` | **선정**. 범용적이고 설치 표면이 짧으며 확장 가능 |
| `project-harness` | 의미는 명확하지만 일반 명사 조합이라 브랜드 식별성이 약함 |
| `workflow-harness` | workflow에 치우쳐 문서·품질·스킬 포트폴리오를 충분히 표현하지 못함 |
| `agent-workbench` | IDE·실험 도구로 오해할 가능성이 있음 |

### 1.2 호환성 정책

plugin ID와 qualified install 문자열은 사용자 설치 계약이므로 이번 변경은 공개
설치 표면의 breaking change다. `0.2.2`의 manifest, archive, tag를 덮어쓰지 않고
`0.3.0`으로 승격한다. 기본 정책은 별도 legacy alias를 만들지 않는 hard cutover다.

기존 사용자는 다음 순서로 이동한다.

```text
기존 ai-agent-harness@ai-agent-harness 제거
→ marketplace hb9397 갱신
→ harness-kit@hb9397 설치
→ 새 세션에서 skill 호출 확인
```

legacy alias를 병행하면 두 plugin ID와 두 cache 경로를 계속 검증해야 하므로 이번
계획에는 포함하지 않는다. alias가 필요해지면 별도 호환성 계획으로 분리한다.

## 2. 완료 정의

다음 조건을 모두 만족해야 이 계획을 완료로 표시한다.

1. Codex·Claude manifest의 `name`이 모두 `harness-kit`이다.
2. Codex·Claude marketplace의 `name`이 모두 `hb9397`이고 plugin source가
   `./plugins/harness-kit`을 가리킨다.
3. 새 설치 명령과 evidence의 qualified ID가 `harness-kit@hb9397`이다.
4. 이전 `plugins/ai-agent-harness-0.2.2.zip`과 SHA-256이 변경되지 않는다.
5. `plugins/harness-kit-0.3.0.zip`과 `maintainer/plugin/release.json`이 동일한
   plugin ID·version·archive hash를 기록한다.
6. 현재 생성물·문서·검증 코드의 live reference가 새 식별자로 정합화된다.
   저장소 이름이 들어간 URL과 역사 문서는 의미를 확인해 보존한다.
7. 루트 `example/`의 11개 파일(총 225,227바이트)이 외부 저장소에 복사되고,
   clone 후 파일 목록·내용·SHA-256이 일치한다.
8. 외부 이관 검증 전에는 루트 `example/`을 삭제하지 않는다.
9. 루트 `example/` 제거 후에도 `skills/**/example` 및 `skills/**/examples`의
   plugin 내부 보호 자산은 그대로 유지된다.
10. `README.md`, `AGENTS.md`, `.user-docs/**`, maintainer 문서가 새 설치명과
    외부 examples 관리 위치를 설명한다.
11. 사용자 프로젝트용 `.docs/**` 계약과 `skills/**`의 사용자 산출 경로는
    변경하지 않는다.
12. projection·plugin build·strict validation·skill eval·CLI smoke·release
    regression이 통과한다.
13. 실제 Codex App·Claude Desktop Code 모델 호출 증적이 없으면 기술 검증 성공과
    별개로 release 상태는 `not-release-ready`를 유지한다.
14. Phase별 구현·검증·커밋을 완료한 뒤에만 push·tag·GitHub Release를 별도 승인으로
    수행한다.

## 3. 기준선과 영향 범위

### 3.1 현재 플러그인 정본

이름은 다음 정본과 생성물에 중복되어 있다. 문자열 전역 치환을 하지 않고 정본을
먼저 수정한 뒤 생성기를 통해 산출물을 재생성한다.

| 계층 | 현재 위치/값 | 목표 조치 |
|---|---|---|
| source constant | `maintainer/skills/harness-plugin-maintainer/scripts/plugin_common.py`의 `PLUGIN_ID`·`PLUGIN_ROOT_REL` | `harness-kit`, 파생 root |
| builder constant | `build_plugin.py`의 `MARKETPLACE_NAME` | `hb9397` |
| manager skill 정본 | `maintainer/skills/harness-plugin-maintainer/**` | 실제 사용자 plugin ID만 새 이름으로 갱신 |
| manager projection | `.agents/skills/**`, `.claude/skills/**` | sync generator로 재생성 |
| plugin runtime | `plugins/ai-agent-harness/**` | builder로 `plugins/harness-kit/**` 재생성 |
| marketplace | `.agents/plugins/marketplace.json`, `.claude-plugin/marketplace.json` | builder 생성 결과 확인 |
| release evidence | `maintainer/plugin/{release,cli-smoke,install-verification}.*` 등 | 새 ID·qualified ID·archive 반영 |
| 사용자 문서 | `README.md`, `.user-docs/**` | 설치·호출·업데이트·제거 명령 갱신 |

현재 `0.2.2` 기준 archive SHA-256은 다음과 같이 보존한다.

```text

016be105eaebf46f164641946c1705edbf1b70bed7a3bf4aff661a6e0814d27c
```

현재 root `example/`은 다음 11개 파일이며, 플러그인 runtime에 직접 포함되는
정본이 아니다.


현재 기준 총 크기는 225,227바이트다. `example/README.md`는 외부 운영문서와
연결되는 독립 인덱스이며, 현재 live 문서에서 root `example/`을 직접 링크하는
참조는 확인되지 않았다. 따라서 plugin runtime 동작에는 직접 영향이 없지만,
저장소 clone 사용자의 학습·수동 검증 자료가 사라지는 문서/운영 영향은 있다.

삭제하지 말아야 할 별도 자산은 다음과 같다.

```text
skills/commit/examples/**
skills/create-prototype/examples/**
skills/design-prototype-docs/example/**
```

이 경로들은 plugin payload 안에서 skill 실행이 참조하는 보호 자산이므로 root
`example/` 외부화와 함께 삭제하거나 이동하지 않는다.

### 3.3 외부 관리 대상

기본 외부 대상은 다음 별도 저장소로 계획한다.

```text
https://github.com/hb9397/ai-agent-harness-examples
```

이 저장소가 실제로 생성·쓰기 가능한 상태인지 확인하기 전에는 root 삭제 Phase를
시작하지 않는다. 외부 저장소 루트에 기존 `example/`의 파일 내용과 파일명 상대
경로를 보존하고, 이 저장소에는 외부 URL·revision·archive SHA-256을 기록한다.

## 5. 전역 안전 규칙

- 이 문서 작성 시점에는 이름 변경과 root `example/` 삭제를 수행하지 않는다.
- `example/`은 보호 자산이므로 외부 clone 검증과 별도 파괴적 변경 승인 전에는
  `Remove-Item`, `git rm`, 이동을 실행하지 않는다.
- `0.2.2` archive와 `v0.2.2` tag는 immutable 기준선으로 취급한다.
- `ai-agent-harness` 문자열을 전역 치환하지 않는다. repository URL,
  historical plan, old archive, migration note인지 live plugin identity인지 파일별로
  분류한다.
- `AGENTS.md`와 `.user-docs/**`가 새 경로·설치명을 설명하기 전에는 root 제거를
  완료로 표시하지 않는다.
- 생성물은 `sync_manager_projections.py`, `build_plugin.py`, 검증기에서만 갱신한다.
- 각 Phase는 구현·검증·커밋을 한 묶음으로 완료한다. push·tag·release는 마지막
  별도 승인 전까지 수행하지 않는다.

## 6. 구현 Phase

### Phase 0 — 기준선·inventory·변경 허용 목록 고정

**목표**: `0.2.2`, plugin identity, root `example/` 보호 자산, 현재 live reference를
수치와 hash로 고정한다.

작업:

1. `git status --short --branch`, `git rev-parse HEAD`, `git show-ref --tags v0.2.2`로
   작업 트리와 tag를 기록한다.
2. `git ls-files example`와 파일별 SHA-256을 기록한다.
3. `maintainer/inventory/example-externalization-baseline.json`을 새로 만들고
   파일 목록·바이트 수·SHA-256·기준 commit을 기록한다.
4. `ai-agent-harness` hit를 live identity, repository URL, historical record,
   old release artifact, migration note로 분류한다.
5. `.docs/**`와 skill-internal `example(s)`가 변경 대상에서 제외되었는지 확인한다.

검증:

```powershell
git status --short --branch
git rev-parse HEAD
git show-ref --tags v0.2.2
git ls-files example
Get-ChildItem -LiteralPath 'example' -Recurse -File |
  Get-FileHash -Algorithm SHA256
git diff --check
git diff --cached --check
```

완료 기준: clean worktree, root example 11개/225,227바이트, 기존 archive hash
일치, baseline JSON 검토 완료.

3. 외부 저장소에서 commit/tag를 만들고 revision을 기록한다.
4. 별도 임시 디렉터리로 clone해 파일 목록·내용·SHA-256을 baseline과 대조한다.
5. 외부 README에 원 저장소와 plugin `harness-kit`의 관계, 예제의 비실행·참고용

중단 기준: 외부 저장소 생성 실패, 권한 불명확, clone 비교 불일치, license/NOTICE

## 7. 위험·rollback

| 위험 | 조기 신호 | 대응 |
|---|---|---|
| 외부 examples 이관 불완전 | clone hash mismatch | root 삭제 중단, 외부 commit 보완 |
| old plugin ID 잔존 | live docs/evidence에 old qualified ID 발견 | old hit 분류 후 live 파일만 정정 |
| generated path drift | build `--check` diff | source constant 수정 후 projection/plugin 재생성 |
| 기존 사용자 cache 충돌 | old/new plugin이 동시에 목록에 노출 | migration 문서와 remove→install 순서 검증 |
| 내부 skill example 손실 | plugin manifest에서 internal path 누락 | root example 삭제를 되돌리고 builder 입력 확인 |
| `.docs` 계약 변경 | `git diff -- .docs` 또는 관련 template diff | 해당 변경 즉시 제거; 사용자 산출 경로는 범위 밖 |
| Desktop/model 증적 부재 | release gate `not-release-ready` | 기술 검증과 readiness를 분리해 상태 유지 |

rollback은 `v0.2.2` tag와 보존 archive를 기준으로 한다. 새 `0.3.0` artifact를
삭제하거나 old tag를 force-update하지 않는다. 외부 examples 저장소 이관이 실패하면
root `example/`은 원래 위치에 남긴다.
