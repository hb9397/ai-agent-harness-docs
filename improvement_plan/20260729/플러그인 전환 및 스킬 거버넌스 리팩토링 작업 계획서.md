## 1. 관리자의 의도와 완료 상태

### 1-1. 저장소와 사용자 플러그인의 역할

1. 이 저장소는 일반 프로젝트 수행자가 복제해 사용하는 저장소가 아니다.
2. 이 저장소는 하네스 관리자가 사용자 스킬 원본, 외부 업스트림, 플러그인 패키지, 릴리스를 관리하는 저장소다.
3. 실제 프로젝트 수행자는 Codex 또는 Claude에서 사용자 플러그인을 설치해 하네스를 사용한다.
4. 별도 관리자 플러그인은 만들지 않는다.
5. 관리자는 이 저장소를 clone해 repo-local 관리자 스킬을 사용한다.
6. 관리자는 배포된 사용자 플러그인도 일반 사용자와 같은 방식으로 설치해 실제 사용 환경을 검증할 수 있다.

### 1-4. 외부 스킬 관리 의도

외부 공식 스킬과 유명 스킬은 다음을 구분해 문서화한다.

1. **참고형(`reference`)**
   - 외부 스킬의 설계 원칙, 워크플로우, 품질 기준만 참고한다.
   - 원본 파일이나 상당한 문구·자산은 포함하지 않는다.
   - 어떤 개념을 어느 내부 스킬에 반영했는지 기록한다.

2. **직접 반입형(`incorporated`)**
   - `vendored`: 원본 파일·자산을 실질적 변경 없이 포함한다.
   - `adapted`: 원본을 번역·재구성하거나 Codex/Claude 중립화, 로컬 규칙 반영 등으로 수정한다.
   - 파일별로 원본 유지·수정·제외·로컬 전용 여부를 기록한다.

`im-not-ai`는 하네스 사용자 플러그인에 내장하되 Codex와 Claude에 맞는 변환이 필요하므로 `reputable-third-party + adapted`로 분류한다.

“GitHub를 통해 바로 최신화”의 주체는 일반 프로젝트 runtime이 아니라 관리자다. 관리자가 GitHub의 최신 안정 릴리스를 확인·고정·검증해 새 하네스 플러그인 버전으로 배포하고, 사용자는 하네스 플러그인 업데이트 한 번으로 그 내용을 받는다.

### 1-5. “하나의 스킬로 최신화”에 대한 확정

외부 참고형과 직접 반입형의 최신 변경 관리 및 새로운 공식·유명 후보 탐색은 **하나의 관리자 스킬 `skill-portfolio-maintainer`로 수행 가능하다.**

단, 같은 절차로 무조건 덮어쓰는 기능을 만들지는 않는다.

| 관계 유형 | 최신 변경 확인 | 실제 반영 |
|---|---|---|
| `reference` | 최신 릴리스·태그·SHA와 현재 참고 내용을 의미 단위로 비교 | 개선 후보 제안 → 승인 → 내부 스킬에 필요한 내용만 반영 |
| `vendored` | 파일 목록·해시·라이선스·Git diff 비교 | 승인된 파일을 원본과 동일하게 반입; 삭제·교체는 별도 승인 |
| `adapted` | 업스트림 기준 SHA와 로컬 변환·패치의 의미 차이 비교 | 승인된 내용을 staging → 플랫폼 변환 → 회귀 검증 후 반영 |
| `native` | 외부 업스트림 없음 | 내부 품질·중복·플랫폼 호환성만 감사 |

책임 경계는 다음과 같다.

```text
skill-portfolio-maintainer
  신규 후보 탐색/등록 upstream 확인 → 차이 분석 → 영향 보고 → 승인 → staging → 반영 → 검증
                                                                        ↓
harness-plugin-maintainer
  사용자 스킬 정본 수집 → 플랫폼 projection → manifest/version → 설치 검증 → 릴리스
```

전체 업스트림의 최신 상태 조회는 한 번에 수행할 수 있다. 실제 반영은 업스트림 하나씩 승인 후 진행한다.

세 관리자 스킬의 경계:

- `skill-portfolio-maintainer`: 기존 스킬의 출처 조사, upstream 변경 제안, 승인된 반영, 회귀 검증
- `custom-skill-design`: 신규 스킬 설계와 기존 스킬의 대규모 재설계
- `harness-plugin-maintainer`: 검증된 사용자 스킬의 패키징, version, 설치 검증, 릴리스

### 1-6. Markdown 산출물 후처리 의도

사용자 스킬이 실제 `.md` 파일을 생성하거나 갱신한 경우, 하네스의 표준 다음 단계로 `humanize-korean`을 이용한 **문서 개선안**을 둔다.

```text
Markdown 생산 스킬
→ 원 스킬의 저장·구조 검증 완료
→ 원본 hash와 보호 토큰 기준선 기록
→ humanize-korean 문서 개선안 생성
→ 의미·구조 불변 검사
→ 원본 대비 diff와 변경 이유 제시
→ 사용자 승인
→ 승인된 변경만 반영
→ 원 스킬의 링크·인덱스·구조 검증 재실행
→ 다음 하네스 스킬로 전달
```

이 단계는 자동 덮어쓰기가 아니다. 개선안 생성은 표준 후처리로 제안하되 사용자가 건너뛸 수 있고, 반영은 diff 승인 후에만 수행한다. 거절·취소·검증 실패 시 원본 hash를 유지한다.

현재 사용자 17종을 실제 파일 쓰기 기준으로 스캔한 적용 대상은 다음 7종이다.

- 필수 생성·갱신: `harness-setup`, `harness-bootstrap`, `context-doc`, `design-prototype-docs`, `impl-doc`, `impl-fe-be-doc`
- 조건부: `design-doc`이 사용자 승인 후 `.md`로 저장된 경우

대화창에 Markdown 형식 리포트만 출력하는 `doc-audit`, `impl-verify`, `impl-reuse-scan`, `multi-review`, `pre-commit`은 파일 후처리 대상이 아니다. 비 Markdown 산출물이 중심인 나머지 사용자 스킬도 대상에서 제외한다.

후처리는 일반 설명의 자연스러움·중복·번역투를 개선하되 제목 계층, 표 구조, 코드 fence, 명령, 경로, 링크, task·RFP·SFR·REQ·API·field ID, 숫자, 날짜, 작성자, 인용·각주, 체크박스, `반드시/금지/선택/승인 후` 같은 의무 수준을 잠근다. `CLAUDE.md`의 `@AGENTS.md` bridge, roadmap index의 기계 소비 영역, 자동 생성 marker는 직접 윤문하지 않는다.

여러 `.md`를 한 번에 만드는 스킬은 파일마다 별도 호출하지 않고 **산출물 묶음 한 번**으로 handoff한다. 사용자가 묶음 전체 또는 일부 파일을 선택하고, 승인된 최종 파일만 후속 스킬의 입력이 된다.

producer가 다른 Markdown producer의 내부 workflow를 재사용하는 경우에는 **최외곽 producer만 handoff owner**가 된다. 예를 들어 `harness-bootstrap` 내부의 `design-doc`·`context-doc` 단계는 child handoff를 억제하고 생성 파일을 상위 bundle에 반환하며, `harness-bootstrap`이 전체 저장·검증 후 한 번만 개선안을 요청한다. 같은 스킬을 standalone으로 호출할 때는 해당 스킬이 owner가 된다.

### 1-7. 비목표

- 사용자 플러그인이 실행 중 GitHub `main`을 직접 pull하지 않는다.
- 일반 프로젝트에 `.agents/skills`, `.claude/skills`를 복사·동기화하지 않는다.
- 관리자 전용 플러그인을 만들지 않는다.
- 외부 스킬의 인기나 별 개수만으로 채택하지 않는다.
- 라이선스가 없거나 재배포 권리가 불명확한 원본을 사용자 플러그인에 포함하지 않는다.
- 외부 최신 버전이라는 이유만으로 기존 템플릿·스크립트·references·assets·examples·evals를 자동 삭제하지 않는다.
- 문서 개선 흐름으로 `SKILL.md`, LICENSE, NOTICE, plugin 생성물이나 제3자 원문을 일반 사용자 산출물처럼 자동 윤문하지 않는다.
- 과거 `improvement_plan/20260627/` 문서의 본문을 현재 상태처럼 일괄 치환하지 않는다.

## 5. 외부 스킬 출처·최신화 모델

### 5-1. 소스 성격

| 값 | 의미 |
|---|---|
| `official` | OpenAI·Anthropic 등 플랫폼 제공자가 직접 관리 |
| `reputable-third-party` | 유명하거나 검증된 외부 프로젝트 |
| `internal` | 이 조직·관리자가 직접 만든 원본 |

“유명함”은 탐색 우선순위일 뿐 라이선스·안전성·적합성을 보장하지 않는다. 별 개수 등 변동 수치는 기록할 경우 확인 날짜를 함께 쓴다.

### 5-2. 도입 방식

| 값 | 원본 포함 | 주요 기록 |
|---|---:|---|
| `reference` | 아니오 | 참고 개념, 확인 SHA, 반영한 내부 위치 |
| `vendored` | 예, 원본 유지 | 파일 해시, 저작권, 라이선스, 원본 경로 |
| `adapted` | 예, 변형 | 기준 SHA, 파일별 변환, 로컬 패치, 제외 이유 |
| `native` | 아니오 | 내부 설계·품질·플랫폼 감사 |

한 업스트림이 혼합형일 수 있다. 이 경우 관계는 `adapted`로 두고 파일별 treatment를 기록한다.

```text
verbatim   원본 그대로 포함
modified   원본을 변형해 포함
excluded   검토 후 사용자 패키지에서 제외
local-only 로컬에서 새로 작성
```

### 5-5. 최신 상태 5단계

`latest` 한 필드로 관리하지 않는다.

| 상태 | 의미 |
|---|---|
| `observed` | GitHub에서 가장 최근 발견한 릴리스·태그·SHA |
| `accepted` | 관리자가 반영하기로 승인한 SHA |
| `embedded` | 현재 사용자 정본 `skills/`에 실제 반영된 SHA·해시 |
| `packaged` | 검증된 사용자 plugin artifact에 포함된 SHA·해시와 plugin version |
| `released` | 사용자가 설치할 수 있는 플러그인 버전에 포함된 SHA |

참고형에는 `last_reviewed_sha`, `last_reflected_sha`를 추가한다. 변형형에는 `upstream_base_sha`, `local_patch_hash`를 추가한다.

### 5-6. 승인 게이트

| Gate | 내용 |
|---|---|
| G0 | 소스 등록·성격·도입 방식 승인 |
| G1 | 저장소 소유자, 릴리스, 전체 SHA 확인 |
| G2 | 라이선스와 제3자 포함물 확인 |
| G3 | scripts/hooks/MCP/네트워크/바이너리/symlink/submodule/권한 변화 분석 |
| G4 | 참고할 개념 또는 직접 포함할 파일 범위 승인; 보호 자산 추가·내용 수정·보완의 영향 승인 |
| G5 | 보호 자산 삭제·이동·교체의 별도 파괴적 변경 승인 |
| G6 | 임시 staging에만 반영 |
| G7 | Codex·Claude·회귀·라이선스 검증 |
| G8 | 정본 승격 후 플러그인 릴리스 흐름으로 인계 |

“최신화해줘”라는 요청은 G4의 자산 영향 승인이나 G5의 파괴적 변경 승인으로 해석하지 않는다.

### 5-7. NOTICE 정본과 생성 범위

- 루트 `THIRD_PARTY_NOTICES.md`: 이 관리 저장소에 보존된 사용자·관리자 직접 반입물 전체
- plugin의 `THIRD_PARTY_NOTICES.md`: 실제 사용자 runtime payload에 포함된 직접 반입물만
- 두 파일은 provenance와 file-map에서 생성하며 각각 직접 중복 편집하지 않는다.

`reference`와 `native`는 source URL과 확인 근거가 필수지만 재배포 라이선스 필드를 강제하지 않는다. `vendored`와 `adapted`는 SPDX, pinned SHA의 LICENSE URL·hash, 저작권·NOTICE가 필수다. 참고 과정에서 원문·번역·자산을 실질적으로 가져오게 되면 즉시 `adapted`로 재분류하고 G2~G7을 다시 수행한다.

## 6. 플러그인·플랫폼 계약

### 6-1. 하나의 사용자 플러그인

사용자에게 보이는 제품과 버전은 하나다.

- plugin ID: `ai-agent-harness` 가칭
- 사용자 논리 기능: 18종
- 관리자 스킬: 포함 금지
- Codex와 Claude release manifest: 동일한 정확한 `X.Y.Z`
- 플랫폼 차이는 생성 runtime projection에서 처리

권장 구현은 `plugins/ai-agent-harness/` 하나에 두 manifest를 두고 각각 다른 runtime 경로를 선언하는 방식이다.

```text
.codex-plugin/plugin.json  → ./runtime/codex/skills
.claude-plugin/plugin.json → ./runtime/claude/skills + ./runtime/claude/agents
```

Phase 6에서 두 플랫폼의 로컬 marketplace로 이 구조를 실제 검증한다. 어느 한 플랫폼이 동일 물리 루트를 허용하지 않으면, 단일 논리 plugin ID와 version을 유지한 채 생성 산출물만 플랫폼별 두 폴더로 분기한다. 사용자 제품을 둘로 분리하지 않는다.

### 6-2. `humanize-korean` 플랫폼 계약

| 항목 | Codex | Claude |
|---|---|---|
| 공개 핵심 기능 | `humanize-korean` Fast 경로 | `humanize-korean` + 승인된 고급 경로 |
| 보조 진입점 | 핵심 스킬 내부 옵션 | `humanize`, `humanize-redo` alias projection |
| agent | 패키지 agent에 의존하지 않음 | 독립 정본의 3종(`humanize-monolith`, `humanize-diagnostician`, `humanize-finalizer`)만 노출 |
| references | 실제 디렉토리로 materialize | plugin root 내부 실제 경로 |
| script path | plugin 내부·플랫폼 중립 | `${CLAUDE_PLUGIN_ROOT}` 기반 |
| 모델 | 하드코딩 금지 | `model: opus` 등 하드코딩 제거 |

저장·재배포 권리를 확인한 업스트림 snapshot만 provenance를 위해 보존할 수 있다. 사용자 runtime에 노출할 agent·scripts·tests는 승인된 exact allowlist로 제한한다. 권리 확인된 snapshot에서 runtime 비노출 파일은 삭제가 아니라 “보존 snapshot에는 존재, 사용자 discovery에는 비노출”로 처리하고, 권리 미확인 파일 내용은 snapshot 자체에 넣지 않는다.

### 6-3. Markdown 산출물 개선 계약

producer 스킬은 `humanize-korean`의 내부 파일 경로나 플랫폼 전용 명령을 참조하지 않고, 공개 plugin skill 이름과 다음 handoff 정보만 전달한다.

- producer skill 이름
- artifact bundle ID, 최외곽 `handoff_owner`, `suppress_child_handoff` 상태
- 생성·갱신된 `.md` 절대 또는 project-relative 경로 목록
- 각 파일의 반영 전 hash
- 잠글 구조·식별자·명령·경로·링크·메타데이터
- 원 producer가 다시 수행할 validator
- 다음 downstream skill과 입력 경로

상태는 `producer-validated → improvement-proposed → user-approved → refined → producer-revalidated`로 관리한다. `user-approved` 전에는 실제 파일을 수정하지 않는다.

중첩 producer는 `suppress_child_handoff=true`일 때 자체 개선 단계를 실행하지 않고 산출물·잠금 정보·validator 정보만 최외곽 owner에 반환한다. validator는 같은 bundle ID의 개선 handoff가 정확히 한 번 발생했는지 검사한다.

| 산출물 유형 | 개선 범위 | 잠금·재검증 |
|---|---|---|
| 설계·prototype·구현 계획 | 설명 문장, 중복, 문단 리듬 | 필수 section, 표, diagram, ID, interface, task dependency |
| AGENTS·instruction | 설명 가독성 | 명령, path, 금지·필수 규칙, import/index 관계 |
| CLAUDE bridge | 원칙적으로 개선 제외 | 정확한 `@AGENTS.md`와 Claude 전용 delta |
| roadmap index | 사람이 읽는 설명만 선택 적용 | 파일명, 링크, 상태, 순서, 현재 위치 |

구조 또는 의미 불변 검사가 실패하면 개선안을 폐기하고 원본을 유지한다. 여러 파일 묶음은 일부 파일 실패 시 승인된 파일까지 임의로 부분 반영하지 않고, 사용자에게 원자적 전체 취소와 명시적 부분 재선택 중 하나를 확인한다.

현재 “스킬 간 참조 금지” 규칙은 **다른 스킬의 내부 파일·상대경로·구현에 대한 결합 금지**로 좁혀 명문화한다. 같은 plugin 안의 공개 skill 이름을 이용한 문서화된 workflow handoff는 허용하되, 수신 스킬 부재 시 원본 산출물만 정상 완료하고 설치·버전 확인 방법을 안내한다.

### 6-4. 설치·업데이트 문서 표면

| 플랫폼 | 설치 표면 | 계획에 포함할 내용 |
|---|---|---|
| Codex | CLI | `codex plugin marketplace add/list/upgrade/remove`로 source 관리, `codex plugin add/list/remove`로 비대화식 설치 관리, `/plugins` 브라우저로 대화형 설치·활성/비활성·제거, 새 세션 |
| Codex | ChatGPT/Codex 데스크톱 앱 | Codex 또는 Work의 Plugins UI, 앱 재시작, 새 task |
| Claude Code | CLI | marketplace 등록, install/update/list, scope, `/reload-plugins` |
| Claude Desktop | Code 탭 | 로컬·SSH session의 Plugins UI와 제약 |
| Claude Chat/Cowork | Customize → Plugins | Claude Code 설치와 별도라는 설명 |

Codex에서 `codex plugin marketplace ...`는 marketplace source 관리, `codex plugin add/list/remove --json`은 자동화 가능한 plugin 설치 관리, `/plugins`는 대화형 browse·install·uninstall·toggle 경로다. 세 표면을 섞지 않는다. 현재 문서화된 독립 `codex plugin update` 명령은 없으므로 marketplace를 upgrade한 뒤 `codex plugin add`로 새 설치를 적용하고, stale하면 `remove/add`하는 보수 절차와 새 session 확인을 둔다. Claude는 version 증가 후 plugin update와 reload 절차를 문서화한다.

### [INIT-04] · 저장소·플러그인 자체 라이선스와 제3자 고지 경계 동결 (`maintainer/plugin/release.json`)

**의존**: INIT-01, INIT-02

현재 루트 `LICENSE`가 없다는 사실을 기준선에 기록하고, 소유자가 다음을 명시적으로 결정하기 전에는 distributable artifact 생성을 차단한다.

- 이 저장소 자체 코드의 라이선스 또는 사내 전용 배포 조건
- 생성 사용자 플러그인의 자체 코드 라이선스 또는 배포 조건
- 제3자 라이선스 파일을 둘 `licenses/**`와 NOTICE 범위
- private/team/public을 모두 포함하는 “배포 가능 payload” 정의

`im-not-ai`의 MIT는 해당 제3자 payload에만 적용하며 통합 플러그인 전체 라이선스로 확대 해석하지 않는다. 권리 불명확 자료는 관리자나 법무 검토를 요청할 수 있지만, 승인만으로 재배포 권리가 생긴다고 간주하지 않는다.

**검증 기준**: 자체 라이선스·배포 조건이 `UNDECIDED`이면 Phase 4 source promote와 Phase 6 package가 fail-closed 된다.

### [INIT-05] · 관리자 자동화 실행·의존성 계약 동결 (`pyproject.toml`)

**의존**: INIT-01

관리자 manifest는 JSON으로 통일하고 Python 3.11+ 표준 라이브러리만 사용한다. 모든 파일 I/O는 UTF-8·LF 정본을 사용하며 Windows·WSL·Linux 실행 계약과 `py -3 → python3 → python` launcher 탐지 순서를 문서화한다. 향후 외부 패키지를 도입하면 같은 변경에서 정확한 버전·hash lock을 추가하지 않는 한 CI를 실패시킨다.

**검증 기준**: YAML parser 같은 암묵적 의존성이 없고, 지원 OS마다 같은 JSON·hash 결과를 만든다.

### [INIT-06] · 임시·build·archive 격리 정책 (`.gitignore`)

**의존**: INIT-05

`.tmp/upstream-stage/**`, `.tmp/plugin-smoke/**`, 검증용 cache, `dist/**`, release archive 임시 파일을 명시적으로 ignore한다. provenance·promotion 증적과 최종 release checksum은 ignore하지 않는다.

**검증 기준**: upstream 원문 staging과 설치 cache가 `git status`에 나타나지 않고, 정본 증적을 실수로 숨기지 않는다.

### [IO-02] · 안정 릴리스·SHA 확인과 임시 snapshot staging (`.tmp/upstream-stage/im-not-ai/`)

### [TEST-18] · 실패·롤백·공급망 검증

**의존**: TEST-16, TEST-17

모든 실패 주입과 rollback은 별도 임시 canonical mirror, 임시 Git history, 임시 plugin marketplace/install/cache에서 수행한다.

- upstream license 변경
- protected asset 삭제
- Markdown 개선안의 task ID·path·명령·의무 수준 변조
- 승인 전 파일 쓰기와 bundle 일부의 비원자적 반영
- malicious script/path
- patch conflict
- manifest version 누락
- plugin install 실패
- private repo 인증 실패
- 새 plugin release 회귀

격리 fixture의 이전 `released` lock과 plugin version으로 rollback한다. upstream `main`을 다시 pull해 되돌리는 방식은 사용하지 않는다. 실제 저장소의 lock·release metadata·plugin artifact와 사용자의 기존 프로젝트는 읽기 전용 검증 대상으로만 다룬다.

### [PKG-19] · 릴리스 후보·배포 승인·released lock (`CHANGELOG.md`, release checklist, tag)

**의존**: TEST-15, TEST-16, TEST-17, TEST-18

- `humanize-korean` upstream tag·SHA
- 플랫폼 capability 차이

**검증 기준**: 배포가 성공한 경우에만 release notes와 manifest·marketplace source·released lock·NOTICE가 같은 버전·SHA를 가리키며, 미배포 후보는 released로 표시되지 않는다.

## 11. 실행 원칙

1. Phase 순서는 원칙적으로 유지한다.
2. Phase 3의 문서 초안과 Phase 4의 legal audit는 병렬 가능하지만, `im-not-ai` release payload 승격은 Phase 3 정책 완료 후에만 한다.
3. 외부 update의 조회·diff는 읽기 전용으로 병렬 실행할 수 있다.
4. 외부 source의 실제 promote는 한 번에 한 업스트림만 수행한다.
5. 생성물보다 정본을 먼저 수정한다.
6. 스킬 수정 후 운영 정본, 소개 문서, README 순으로 갱신한다.
7. 기존 사용자 산출물과 보호 자산은 기본 보존한다.
8. 보호 자산 추가·내용 수정·보완은 자산 영향 승인, 삭제·이동·대체는 별도 파괴적 변경 승인과 영향표를 남긴다.
9. Markdown 개선안은 원 producer 검증이 끝난 뒤 생성하고, 보호 token과 사용자 승인 없이 원본을 수정하지 않는다.
10. plugin 설치 검증 전에는 “Codex·Claude 지원 완료”로 표시하지 않는다.
11. release는 모든 DoD와 관리자 최종 승인을 통과한 뒤 수행한다.
